## 0. 先把两件事分开：改产品 ≠ 练评测

这是"老停留在改 AI 助手"的根因 —— 两者被混在一件事里了。

| | 改产品（这几天在干的） | 练评测（真正想干的） |
|---|---|---|
| 目标 | 让系统**行为变好** | 让"行为好不好"**可测量、可复现** |
| 产出 | 一个能演示的功能 | 一套能复用的**评测集 + 指标 + 报告** |
| 判据 | 演示时好看 | **数字能不能支撑结论** |
| 最危险的失败 | demo 崩了（看得见） | **测了个假东西还绿着**（看不见） |
| 简历句式 | 「实现了 XX 功能」 | 「设计 N 条评测集，准确率 X%，发现 Y 类缺陷」 |

**关键判断：两条线没有优劣，但它们的工作对象不同。**
改产品的对象是**源码**；练评测的对象是**评测集 + 指标**。
之前每次讨论都从"这条回答怪怪的"（产品视角）入口，所以每次都被拽回改代码。
—— 不是定力问题，是**入口**问题。

### ⭐ 关于 Mock，一个视角转换（重要）

**Mock 的价值不是"省钱"。** 省下的那点钱（全量一轮 ≈¥0.2~0.6）不值得为它写任何东西。
Mock 的真正价值是这三件**用真模型做不到**的事：

1. **测故障路径** —— 模型 500 / 超时 / 返回空 / 返回脏 JSON 时，系统怎么表现？现在**一条都没有**（因为真模型不会按你要求出错）
2. **确定性地测预算** —— 延迟、token 数上限。真模型跑一次变一次，没法当断言
3. **让评测能进 CI** —— 不依赖外网、不依赖 key、不花钱，才可能每次提交都跑

这才是"评测自动化工程"的核心能力，也是简历上比"写了 N 条用例"更有分量的一句。

## 3. 一个被忽略的事实：你项目里已经躺着方法论了

你以为自己在"改 AI 助手"，其实 `tools/` 下两个脚本的注释里，写着相当标准的评测方法论 —— 只是从没被提炼成"体系"：

| 出处 | 里面写着的方法论 | 对应能力线 |
|---|---|---|
| `jailbreak_report.py` | 「不是'通过率'，说'**被攻破**'更直白」→ **指标口径要贴业务语义** | 1 |
| 同上 | 「整体 30% 里可能藏着'B1 全挡住、B3 全漏'」→ ✅ **必须分桶，平均值会掩盖差异** | 1 |
| 同上 | 「攻破率是**一次采样**测出来的……要下结论得重复采样」→ ✅ **区分快照与结论** | 1 |
| 同上 | 「**先出报告、不先写用例**，因为还不知道哪些攻击能得手」→ ✅ **先探测后固化** | 1 |
| `latency_report.py` | 「用例的产出是红绿，报告的产出是**数字**」→ **报告 vs 断言** | 1 / 5 |
| 同上 | 「把'耗时不超过 3 秒'写成 assert 会随机变红 —— 随机变红的套件比没有套件更糟」→ ✅ **不稳定断言会毁掉整套的可信度** | 5 |
| 同上 | 「这是**能力的边界**，不是偷懒 —— 标清楚，比编一个假指标强」→ ✅ **诚实降级** | 1 |
| `data_loader.py` | 把**期望值编码进 Excel 工作表名**，样本与判据分离 | 1 |

**这四条（分桶、快照≠结论、先探测后固化、报告≠断言）是评测方法论的核心，你已经有了。**
缺的不是"知道"，是**把它们从两个脚本里抽出来、变成每个工位都能用的公共设施**。

**为什么 H1 排第一：**
1. 它是**地基** —— H2~H4 的指标都靠它算；
2. 它**不花钱**（离线算现有结果）；
3. 它最像"测评工程师"而不是"写用例的"：把红绿升级成数字。

**为什么 H3 最值钱：** [4] 准确性/幻觉集是最能体现评测水平的工位（金标集 + judge + 一致性校准），也最难 —— 但必须先有 H1 的指标层才能量出来。

**⚠️ H3 开工前必须先做的一件事：把 H2/H2+ 的三份新用例实跑一遍。**
上下文 5 条 + 注入 13 条 + 越权 5 条，写的时候后端没起，**全部没有真实观测**。
这次跑不是为了看红绿，是为了**校准判据**：
- 上下文里「8 轮后还记不记得」「多轮注入会不会被继承」是**探测型**，期望值要按真实回答复核；
- 注入的 `position=prefix` 窗口取的是 40 字符，要用真实回答确认模型的开场白有没有超出这个窗口；
- 越权的断言依赖 `other_user` 夹具能注册成功，要先确认注册链路不受限。

**判据没校准就去做 judge，等于在流沙上盖楼** —— judge 也是判据，判据错了，judge 只会把错误放大成"有指标的错误"。

## 5. H1 详设（原计划）→ ✅ 已落地（2026-10-14 同日完成）

### 要写的东西

`tools/eval_runner.py` —— 把现有"脚本式报告"推广成**通用评测运行器**：

```
评测集 yaml  ──>  [运行器]  ──>  results/eval_<集名>_<时间>.json   （每条全量留痕）
                     │
                     └──>  指标报告（控制台表 + xlsx）
```

### 关键设计点（这些点本身就是"练"）

| # | 设计 | 为什么 |
|---|---|---|
| 1 | **期望值与数据分离** | 期望值进 yaml，不进代码（铁律 2 的自然延伸）；改判据不碰用例 |
| 2 | **指标要分桶** | 整体数字会掩盖"某类全漏"（照搬 jailbreak_report 的教训） |
| 3 | ⭐ **全量留痕 actual 原文** | 不只存红绿 —— 存了原文，才能**事后改判据重算，不用重跑**（这是省钱和提速的关键，也是你上次批评的根源） |
| 4 | ⭐ **必须有"误拦率"** | 只测"挡住了没"会诱导你越收越紧，直到正常问题也被挡。**安全测试一定要配反向用例**（`test_normal_diet_question_is_not_blocked` 已有雏形） |
| 5 | **判据类型分派指标** | 分类类→准确率+混淆矩阵；拦截类→攻破率+误拦率；一致性类→一致率 |

### 顺带能立刻算出来的指标（拿现有 157 条的结果）

- 意图分类：5×5 混淆矩阵、准确率、每类 P/R/F1
- 安全拦截：攻破率（B1/B2/B3 分桶）、**误拦率**（正常问题被挡的比例）
- 一致性：流式 vs 非流式 intent 一致率

> ⚠️ 前提：现在的 pytest 结果里**只留了红绿**，`actual intent` 没落盘 → 要么运行器自己重跑一遍（有成本），要么先给 conftest 加一个"结果落 JSON"的钩子（无成本，之后永不再重跑）。

### ✅ 实际落地（2026-10-14）：两个零件 + 一条数据流

上面 5 个设计点**全部按原计划实现**，选择的是"加钩子"那条路（无成本、一次到位）。

| 零件 | 干什么 | 成本 |
|---|---|---|
| `common/eval_record.py` | **留痕**：pytest 运行时把每次问答的真实观测（问题 / intent / source / blocked / **回答全文**）与每个用例的结果攒起来，会话结束落 `tools/eval_results.json` | 0（纯旁路） |
| `tools/eval_runner.py` | **算指标**：读留痕 JSON + 数据集 yaml → 混淆矩阵 / P-R-F1 / 漏拦率 / 误拦率 / 攻破率分桶 → 控制台表 + `docs/AI助手-评测报告.md` | 0（离线） |

```
pytest 跑一次 ──> tools/eval_results.json（actual 全文留痕）
                        │
                        └─> tools/eval_runner.py  ← 想怎么算就怎么算
                            （改口径不用重跑模型 = 省钱 + 提速的正解）
```

**怎么做到"不改任何用例"（守住铁律 1）：**

- 观测埋在 `test_cases/ai_assistant/conftest.py` 的 **`ask` 夹具**里 —— 所有 AI 行为用例问模型都要过这个口子，一处埋点全覆盖，`test_*.py` **一个字没改**。
- 结果埋在顶层 `conftest.py` 三个钩子：`logstart` 记"现在在跑谁"、`logreport` 记结果、`sessionfinish` 落盘。
- ⭐ **期望值不用传**：nodeid 里带着参数 id（就是数据集里的 `name`），运行器拿它精确 join 回 yaml。比按问题文本匹配可靠得多 —— 数据集里「你好」在意图集和拦截集里**都有**，按文本 join 会串台。

**指标口径（口径错了数字就是假的）：**

| 工位 | 指标 | 为什么是它 |
|---|---|---|
| [1] 意图识别 | 5×5 混淆矩阵 + 每类 P/R/F1 + 准确率 | 分类问题的标准口径；只有准确率看不出"哪类被判错、错到哪儿去了" |
| [2] 输入安全 | **漏拦率** + **误拦率**（分类型分桶） | 只算漏拦会诱导把规则越收越紧，直到正常问题也被挡 —— 两个必须一起看 |
| [2][5][6] 红队 | 攻破率（B1~B4 分桶）+ **"没测到模型"单列** | 平均值会掩盖"B1 全挡住、B3 全漏"；被硬拦吃掉的样本不能算守住的功劳 |

**防刷分设计：**

1. 每个桶样本数 < 5 自动打 ⚠️（小样本的百分比没有统计意义）；
2. 报告里明写"**攻破率是一次运行快照**，没写 repeat 的样本绿了 ≠ 防线稳"；
3. 报告里明写"标签集与分类器关键词同源 → **高分不能外推**为泛化能力"。

**用法：**

```bash
python tools/run_tests.py test_cases/ai_assistant -q   # 跑一次，自动留痕
python tools/eval_runner.py                            # 离线出指标（0 成本）
python tools/eval_runner.py --md docs/AI助手-评测报告.md
python tools/eval_runner.py --selftest                 # 只自测指标算法（不读文件、不调模型）
```

**遗留（下一轮可选）：** 输出只有控制台 + Markdown，**没做 xlsx**（原计划里写了）——
先把口径跑通更重要；要 xlsx 时在 `render_markdown` 旁边加个渲染器即可，数据早就在 JSON 里了。
