## 一、架构分层类

### Q1：一个接口自动化框架应该分几层？为什么要分层？

**标准答案**：分 4 层，每层只解决一件事，上层依赖下层、下层不知道上层：

```
用例层（test_cases/）   ← 只表达"测什么"，不含 URL、不含发请求细节
   ↓
业务/接口层（api/）      ← 一个接口 = 一个方法，URL 只写在这里
   ↓
底座层（BaseApiClient）  ← Session 复用、超时、日志、断言器（assert_ok/assert_error）
   ↓
工具层（common/ config/） ← 读数据、连库、日志、报告、清理，与业务无关
```

**判断分层好坏的标准只有一条：改一个东西要动几处。**

**本项目证据**：
- `api/__init__.py` —— 总入口 `Api`，用例里写 `api.auth.login(...)` / `api.user.get_profile(...)`，**用例里一个 URL 字符串都没有**。
- README 第五节约定 10 记录了这个决定的账本：收敛前 `/user/profile` 这一条路径在用例里出现 **17 次**，`/recipe/detail/{id}` 散在 2 个文件里；后端改路径时改漏一处 = 一条莫名其妙的假红。收敛后只改 `api/` 里**一行**。

### Q2：接口封装层（`api/`）具体怎么设计？有哪几个坑？

**标准答案**：一个接口封装成一个**动作名**的方法，变量走参数，实测出来的坑写进 docstring。

**本项目证据**（`api/base_api_client.py` + `api/assistant_api.py`）：

| 设计点 | 做法 | 为什么 |
| --- | --- | --- |
| 方法命名 | `get_profile` / `save_goal` / `search` | 动作名，不写 `get` / `do` |
| 路径带变量 | `detail(recipe_id)`、`list_messages(cid)` | 变量做成参数，不写死在方法里 |
| base_url 做成**类属性** | `class KbApi(BaseApiClient): base_url = KB_BASE_URL` | 绝大多数 client 用默认值，只有连 Flask 的要改，改一行类属性比每个用例传参省事 |
| 断言器用 `staticmethod` | `assert_ok` 不写 `self` | 它只检查传进来的响应，跟"谁发的请求"无关；不写 self 更诚实 |
| 逃生舱 | `raw_get()` 只给"故意打非法路径"的越权探针用 | 正常业务用例用它 = 把 URL 又写回用例 |

**坑**：
1. **`Api` 故意不继承 `BaseApiClient`**。早期版本继承了，结果 `api.post("/随便什么路径")` 也能跑通 —— URL 又多了一条偷偷漏回用例的路，而且**不报错**。现在不继承，写 `api.post(...)` 直接 `AttributeError`，防线从"约定上不写"变成"结构上不给"。
   > 注意 README 约定 11 里还留着旧结论（"Api 现在也带着继承来的 get/post"）—— 和当前代码矛盾，**以代码为准**。这正好是 Q25「文档漂移」的现实案例。
2. **流式接口要在 api 层读完再返回**。`chat_stream()` 里 `stream=True` + `decode_unicode=False` 两个都踩过：不加 `stream=True`，requests 会把整条流读完才返回，"能不能流式"就永远测不到（永远通过）；SSE 的 Content-Type 不带 charset，requests 会按 ISO-8859-1 解，中文乱码。

## 二、断言设计类（这一块最能拉开差距）

### Q3：接口断言只校验 HTTP 200 有什么问题？

**标准答案**：能发现"请求没通"，发现不了"通了对不对"。至少要说全四层：

| 层 | 校验什么 | 漏了会怎样 |
| --- | --- | --- |
| HTTP 状态 | 200 / 400 / 401 / 403 | 网关 502 被当成业务 500 |
| 业务 code | `body["code"] == 200` | HTTP 200 但业务失败（很多后端这么设计） |
| 响应结构/契约 | 字段齐不齐、类型对不对、枚举越没越界 | 前端取到 `undefined` → 白屏；`userId` 从 `1` 变 `"1"`，前端 `===` 全失效 |
| 业务语义/副作用 | 写进去的值读回来对不对；越权被拒后数据**真的没变** | 后端"先改再校验"，返回 400 但数据已经脏了 |

**本项目证据**：
- 第 1、2 层 → `BaseApiClient.assert_ok()`：HTTP 200 + `body.get("code") == 200`。**特意用 `.get()` 而不是 `["code"]`** —— 原来 code 缺字段直接 `KeyError: 'code'`，看不出是"契约坏了"还是"用例写错了"。
- 第 3 层 → `common/schemas.py` 的 JSON Schema（draft-07）+ `assert_ok(..., schema=...)`。
- 第 4 层 → `test_notification_idor.py::test_intruder_mark_read_does_not_actually_change_data`：越权被拒之后，用**owner 自己的接口**回查，证明 `is_read` 真的还是 false。

### Q4：`assert_ok` / `assert_error` / `assert_forbidden` 为什么要拆成三个？

**标准答案**：因为它们对应**三套不同的响应体系**，用一把尺子量会量歪。

**本项目证据**（`api/base_api_client.py`）：

| 断言器 | 对应体系 | 响应长什么样 |
| --- | --- | --- |
| `assert_ok` | 成功 | `{"code":200, "message":"...", "data":{...}}` |
| `assert_error` | 业务失败（400） | 统一信封，有 code 有 message；**但 401 的响应体是空的**（所以空体时只验 HTTP，强制 message 传 None） |
| `assert_forbidden` | 权限拒绝（403） | Spring Security 在**进业务层之前**拦的，给的是框架默认体 `{timestamp,status,error,path}`，**没有 code 也没有 message** |

两个细节值得单独记：
1. **`assert_error` 的文案默认精确相等，`contains=True` 要显式打开**。因为"手机号格式不正确"和"手机号格式不正确，请重填"都会通过包含匹配 —— 断言被悄悄削弱了。
2. **`assert_forbidden` 不验格式，验三件安全上必须成立的事**：① 必须 403（不是 500，"崩了"≠"拦住了"）；② **响应体里不能有 `data`**（这是真正有杀伤力的一条：哪天权限判断从 Security 挪进业务层却写漏返回分支，很可能返回 `{"code":403,"data":[用户列表]}`，只断 403 就放过了）；③ 不能是 `code == 200`（那是越权成功了）。
   > 已知缺陷 #10：403 不走统一信封。这里**故意不去断言"必须是 Spring 默认体"** —— 那等于把缺陷当正确答案钉住。缺陷单独用一条 xfail 标记，修好那天变 XPASS 提醒摘标记。

### Q5：怎么保证"契约层（schema）"自己不写错？如果 schema 写错了，会引起什么问题？

**标准答案**：**契约层自己有 bug，后面所有接口用例都会假绿，而且看不出假绿**。唯一能提前发现的办法是给断言层写自测 —— 也就是"测试的测试"。

**本项目证据**：`test_cases/contract/test_契约层_自测.py`，28 条，纯内存、不连服务、秒级。
- 关键做法：**每条"该报错"的用例不只断言"抛了 AssertionError"，还断言报错里点到了对的字段**。只断"抛异常"的话，判据写歪也能过。
  ```python
  with pytest.raises(AssertionError) as exc:
      check({"a": 1}, schema)
  assert "缺少必填字段 b" in str(exc.value)   # ← 必须点名 b
  ```
- 一次列全而不是发现第一个就抛：字段漂通常是"整批一起漂"（后端换了 DTO），逐个跑太慢。

**schema 的两条刻意取舍**（`common/schemas.py` 头部）：
1. **不写 `additionalProperties: False`** —— 后端**新增**字段是向后兼容的，不该让测试红。会红的只有"删字段 / 改类型 / 枚举越界"。
2. **数组只验"是数组"，不验元素** —— 实测空数组时看不到元素结构，现在拿空数组猜元素长什么样 = 编。⚠️ 代价：空数组永远通过 schema，"必须非空"要开发例单独断 `len()`。

> 还有一条纪律值得背：**全部字段来自实测（真打接口抓的响应），不是照 DTO 猜的**。猜出来的 schema 会把"后端本来就错的地方"当标准。

### Q6：什么是"假绿"？本项目里有哪几种假绿，怎么防的？

这是本项目最值钱的一类经验，面试时能讲透会明显加分。

| 假绿场景 | 危害 | 本项目怎么防 |
| --- | --- | --- |
| **模型不可用，后端仍返回 200 + 固定错误文案** | p1 里大量弱断言（"没有违禁词 / 长度够"）会把固定错误文案判成 passed | `conftest.py::_probe_model()`：跑 p1 前用一条真实聊天确认 `source == "deepseek"` 且不含错误标记，否则中止整场 |
| **越权用例只断 403，没有正角色对照** | "接口整个坏了、永远返回 403"也能让全部用例绿 | `test_admin_authz.py` 第 6 节：admin 调同样的接口必须 200 |
| **越权用例只断响应码，不回查副作用** | 后端"先改再校验"，返回 400 但数据已脏 | `test_notification_idor.py`：越权后用 owner 视角回查 `is_read` 真的没变 |
| **越权样本用"不存在的 id"** | 后端在查库之前就拒了，归属校验那行根本没被执行 | 夹具造**真实存在**的通知/会话；AI 越权夹具甚至先往 B 的会话里**塞一条消息**（空会话漏校验时 A 读到的也只是 `[]`） |
| **契约层自己有 bug** | 后面全部用例假绿 | `contract/test_契约层_自测.py` 28 条 |
| **探活没通过却打出"没有失败用例 ✓"** | 一条用例都没跑，看起来是绿的 | `conftest.py::pytest_terminal_summary`：`total_n == 0` 时改打 `_abort_reason` |

## 三、测试数据类

### Q7：数据驱动（DDT）怎么做？支持哪些数据源？

**标准答案**：用例只拿 `list[dict]`，数据存哪、什么格式**对用例透明**。换数据源不改用例。

**本项目证据**（`common/data_loader.py`）：支持 **JSON / CSV / YAML / XLSX** 四种，`load_cases(filename, int_fields=(), sheet=None)` 统一返回 `list[dict]`。

`data/` 目录下同一份 6 行登录数据有 **4 个孪生版本**（`.json` / `.csv` / `.yaml` / `.xlsx`），专供对比演示。`test_login.py` 里换数据源只改一行的文件名：

```python
CASES = load_cases("login_登录_cases.yaml")   # 换成 login_cases.xlsx 也行
```

**踩过的坑（面试常考细节）**：
- **CSV 读出来全是字符串**：`200` 变成 `"200"`，需要 `int_fields=("want_http", "want_code")` 转。所以 `test_login.py` 特意写了一句注释提醒。
- **Excel 在中文 Windows 存 CSV 两个坑**：UTF-8 **带 BOM**（第一列表头变成 `"\ufeffname"`）、GBK/ANSI。解法是 `utf-8-sig` → 不行再退 `gbk`。
- **Excel 多工作表**：`sheet="*"` 读全部，每行多一个 `_sheet` 键记着来自哪张表 —— **这能把期望值编码进表名**（工作表「出题-单选题」→ 这一表的用例都期望识别成"出题"意图）。加一批样本 = 加一张工作表，用例代码一行都不用改。
- **`sheet` 参数传给非 Excel 文件直接报错**，不静默忽略 —— "传了却读到全部数据"是最难查的那种错。

### Q8：测试数据怎么管理？脏数据怎么清理？如何避免两条用例互相污染？

**标准答案**：三道防线 —— **造数据的粒度**、**yield 夹具 teardown**、**进程级清理登记表兜底**。

**本项目证据**：

1. **粒度匹配**：只测 A 资源的用例，夹具不该顺手去动 B 资源（白花请求，还多一份数据风险）。
   - `health/conftest.py::health_user` 造一个**一次性靶子账号**，因为它测的 `/health/info` 是 upsert，每 POST 一次还会往 history 表**追加一条**。
   - `user/test_user_profile.py` 改的是**单例资源**（改它 = 改全局），所以用 `restore_profile` 先备份、后还原。
2. **yield 夹具**：`yield` 之前 setup、之后 teardown，**用例成功还是失败都会执行**。
3. **登记表兜底**（`common/cleanup.py`）：夹具创建资源时登记，正常清完注销；会话收尾 `pytest_sessionfinish` 时把仍登记过的再删一次。夹具写漏了 / 清理到一半抛异常，也不会静默留垃圾。
   - ⚠️ **只回收本进程登记过的资源，不按 username 前缀扫全库** —— xdist 多 worker 并发时扫全库会误删别的 worker 正在用的账号；前缀也不是安全边界（真实用户完全可能叫 `hx_xxx`）。
4. **"有东西没清掉"必须看得见**：之前开发库堆了 112 个临时账号（`pf_` / `hx_` / `np_`），跑了几十轮没人发现 —— 因为只写了日志，而人只看屏幕上那句"没有失败用例 ✓"。现在强制打到终端上。
   - **为什么不让整场失败**：清理失败往往是环境问题（后端连错库），算成"用例失败"会污染通过率这个数字。要的是**看得见**，不是混进失败统计。

**踩过的坑（可以现场讲的故事）**：
- `health_info_history` 上有外键指向 `user(id)` 且是 `ON DELETE RESTRICT`，直接 `DELETE user` 会炸 `IntegrityError(1451)`。所以清理顺序必须是 **孙 → 子 → 父**（message → history/info/goal/record → user）。
- 早期清理"自己写 4 句 DELETE、不看 affected、最后无条件注销"，结果开发库漏了 65 个 `hx_` 账号 —— 后端连开发库时 DELETE 打在测试库上，`affected` 全是 0，照样"清完了"。现在 `purge_user()` **删完会回查确认**，删不干净就抛异常，只有真删掉了才注销登记表。

### Q9：单例资源（改它 = 改全局状态）怎么测？

**本项目证据**：`user/test_user_profile.py` 的 `restore_profile` 夹具 —— 备份 → 测 → 还原。和 `health/info` 的 `info_env` 是同一个思路，但粒度不同：health 是"造个新账号"，user 是"备份再还原"。

还要配一条用例守"局部更新不冲掉别的字段"：`test_update_single_field_keeps_others`。

## 四、pytest 机制类

### Q10：fixture 的 scope 怎么设计？scope 混用会出什么问题？

**本项目证据**（`conftest.py`）：

| 夹具 | scope | 为什么 |
| --- | --- | --- |
| `api` | session | `Api` 本身无状态，整场共用一个 `requests.Session` 是安全的（单进程串行）；Session 复用同一条 TCP 连接 |
| `_auth_state` | session | 登录状态整场只需要一份 |
| `token` / `auth_headers` | function | 只从 `_auth_state` 取**当前** token，用例一行不用改 |
| `admin_headers` | session | 登录要打一次接口 + 一次 bcrypt（~100ms），每条用例都登纯属浪费 |

**坑（面试很可能追问）**：
1. **`ScopeMismatch`**：session 级夹具不能依赖 function 级夹具。所以 `api` 从 function 级改成 session 级时，登录状态也必须跟着提到 session 级。
2. **token 为什么不做成 session 夹具，而是做成对象 `_SessionAuth`**：
   > token 是**字符串**，拿到手的用例改不了它。后端重启 / JWT 过期后，旧字符串会一直用下去。
   > 做成对象后，`auth_headers` 每次按**当前** token 生成，重登后自然拿到新值。

### Q11：怎么实现"整场只登录一次"，又不破坏"故意用错 token 测 401"的负向用例？

这是本项目最精巧的设计之一，强烈建议准备。

**标准答案**：401 自动重登，但**只重登"用当前 token 发出"的请求**。

**本项目证据**（`base_api_client.py::_request` + `conftest.py::_SessionAuth.refresh`）：

```
请求发出 → 401？
  ├─ 钩子问一句：「这次请求实际带的 Authorization 是不是当前会话 token？」
  │     · 是  → 重登、换新 token 重发一次
  │     · 不是（没带 / 伪造 / 别人的 token）→ 原样返回 401
  └─ 不是 401 → 原样返回
```

两个细节：
- **钩子放在模块级**（`_on_unauthorized`），不是实例上。因为 `Api` 聚合了 7 个 client，逐个挂钩子既啰嗦又容易漏掉新加的接口类。
- **重登后直接在原 headers 上改，不复制**。`auth_headers` 是**每条用例一份**的字典，同一条用例后面还会拿它发好几次请求；只改副本的话，第二次请求又带着旧 token，钩子会以为"这不是当前 token"而不再重登。

**效果**：登录次数从"每条用例一次（293 次）"降到"整场 1 次"。

### Q12：`parametrize` / `-m` 标记 / 自动打标签怎么用？

**本项目证据**：
- **参数化**：`test_login.py`、`test_assistant_安全拦截.py` 都是 `@pytest.mark.parametrize("case", CASES, ids=case_name)`，用数据里的 `name` 当**中文用例名**。还需要 `pytest.ini` 里开 `disable_test_id_escaping...= True`，否则中文被转义成 `\u6b63\u5e38`。
- **分层标记在收集阶段自动挂，用例文件零改动**：
  ```python
  def pytest_itemcollected(item):      # 必须早于 -m 过滤
      module = _module_of(item.nodeid)
      if module in {"auth","health","user","toolbox","contract"}:
          item.add_marker(pytest.mark.smoke); item.add_marker(pytest.mark.p0)
      elif module == "ai_assistant" and filename in {"test_assistant_安全拦截.py"}:
          item.add_marker(pytest.mark.p0)     # 确定性安全拦截，不调模型
      elif module == "ai_assistant":
          item.add_marker(pytest.mark.p1)     # 依赖模型，慢且有波动
  ```
- **Allure 层级标签也按 nodeid 自动推**：目录名 = 模块、文件名 = 资源，标签从项目约定里长出来，**零维护**。逐个加 `@allure.feature(...)` 的代价不是"多打几行字"，而是**加新用例时一定会忘**，忘了就掉进报告里一个无分类的孤儿。

**踩坑**：
1. **`pytest_collection_modifyitems` 在同一模块里写两次，后一个会把前一个覆盖掉** —— 不报错、不警告，表现就是"一条都没跳过"。所以根 conftest 只有一个 `trylast` 的 hook。
2. **`def pytest_collection_modifyitems(items)` 的返回值被忽略** —— 必须原地 `items[:] = ...`，`return` 新列表等于什么都没做。
3. **子目录 conftest 的 hook 收到的是全量 items**，必须按路径过滤，否则会把别的模块也一起标成 `requires_db`。

### Q13：xfail 怎么用？XPASS 和 FAILED 为什么必须区分？

**标准答案**：`xfail` = "已知缺陷，等着修"，`skip` = "这条没写"。**两者混在一起，真缺陷会被当成没写而永远没人管**。

**本项目证据**：
- `user/test_user_profile.py` 用 `xfail` 钉住缺陷 #9（`PUT /user/profile` 后 `updateTime` 不刷新）。后端修好那天它会自己变 **XPASS** —— 那就是"可以摘标记了"的提醒。
- 摘标记的正确姿势：**函数名从 `test_bug_xxx` 改成描述契约的名字**（如 `test_negative_age_rejected`）。health 那 4 条 2026-09-29 就是这么转正的，现在再退化会**直接变红**。

**技术坑（这一条很多人不知道）**：
> pytest 对 **strict XPASS** 的处理是 `rep.outcome = "failed"` + `rep.longrepr = "[XPASS(strict)] 原因"`，**却不设 `rep.wasxfail`**。
> 所以只认 `wasxfail` 的代码会把它当成普通回归失败 —— 而这两件事含义完全相反。

`conftest.py::_is_xpass()` 专门认 `"[XPASS" in report.longreprtext`，然后在三处分别处理：`pytest_report_teststatus`（显示）、`_record_outcome`（评测留痕）、结尾汇总的失败清单（标成 `✘ XPASS` 而不是 `✘`）。

## 五、环境与稳定性类

### Q14：怎么保证"跑不起来的时候，报错是人能看懂的"？

**标准答案**：**环境预检 + 明确中止**，而不是让 387 条用例红成一片、真正原因埋在各条 traceback 里。

**本项目证据**（`conftest.py`）：

| 探活项 | 方式 | 关键细节 |
| --- | --- | --- |
| MySQL | `SELECT 1` | 库不存在（错误码 1049）→ 直接给出建库命令 `..\database\rebuild_test_db.bat` |
| 后端 | 先自动补建账号，再 `POST /auth/login`，然后**查测试库对账** | 用 `userId + username` 两个字段比对 —— 只比 userId 不够，两个库里都可能恰好有 `id=1` |
| 算法服务 | `GET /api/kb/stats` | 不用 `/search`（探活不该触发真实检索）；`stats` 会懒加载索引，能把"服务在但索引坏了"这种半启动状态也拦下来 |
| 模型 | 一条真实聊天，验 `source == "deepseek"` | 见 Q6 假绿 |

**三个设计决定值得讲**：
1. **为什么放在 `pytest_collection_finish`，而不是 session 级 autouse 夹具**：夹具要等"第一条用例 setup"才执行，那时中止会把首条用例记成 setup ERROR；`collection_finish` 在收集完、一条还没跑时触发，退出最干净。
2. **探活刻意不复用 `BaseApiClient`**：它会用业务超时、还会往 Allure/日志里记一条**假请求**。探活只是环境检查，不该在报告里留下业务痕迹。所以 `common/accounts.py` 有 `ensure_account_raw()` 裸 requests 版。
3. **xdist 下 controller 统一探一次**：worker 各自探活会重复建账号、重复打 Flask，启动反而更慢。

`_probe_reason()` 把 `requests` 那 300 字符的原生报错翻成一句人话："连不上（服务没启动）" / "探活超时（进程在，但没响应）"。

### Q15：测试不稳定（flaky）有哪些来源？本项目遇到并解决了哪些？

**本项目真实遇到的 6 类**（每条都能讲一个故事）：

| # | 来源 | 现象 | 解法 |
| --- | --- | --- | --- |
| 1 | **时间精度耦合** | `test_update_time_refreshed_on_write` 写 `assert after != before`，单跑 6/6 通过，跟文件一起跑 4/4 失败 —— 前一条用例 teardown 刚 POST 过，两次写入落在**同一秒**，而 `updateTime` 精度只到秒（实测相隔 0.2 秒的两次写入返回同一个值） | 改判"**是否贴近当前时刻**"：`abs(now - after) <= 300s`。既不受秒精度影响，也照样能抓住原 bug（旧值停在几个月前） |
| 2 | **只重试网络失败** | 断言失败重试多少次都不会变绿，反而掩盖真问题 | `pytest.ini` 用 `only_rerun` 正则精确限定 `ConnectionError / ReadTimeout / Max retries exceeded / Connection reset` |
| 3 | **单用例超时** | 某条请求卡死会拖住整场 | `timeout = 180`；⚠️ Windows 走 thread 杀不掉卡死线程、超时会 dump 栈并终止整场，要"单条独立失败"得在 Linux/CI 上跑 |
| 4 | **并行下共享内存** | AI 评测留痕是进程内内存，worker 之间无法合并 | 默认**不**并行；需要时显式 `-n 4 --dist=loadscope`（同模块落同一 worker），并接受"每个 worker 各登录一次" |
| 5 | **模型波动** | 同一句话问两次结果不同 | `pytest-rerunfailures` 的 `pass^5` 思路 + 把能用代码确定性判断的挪进"硬拦"用例（见 Q17） |
| 6 | **项目自身的 bug** | 见 #1 | —— |

### Q16：怎么处理"跑第二次就红"？

**标准答案**：测试数据必须**唯一化** + **可回收**。

**本项目证据**：
- 注册用例用**时间戳 / uuid 唯一值**造账号（`pf_` / `hx_` / `np_` / `ot_` 前缀），配 yield 清理夹具。
- `common/accounts.py` 做**账号自愈**：登录失败就注册，注册失败就给一句人话（"账号已存在但密码不符 → 改 `AUTOTEST_PASSWORD` 或重建测试库"）。
- **注意一个反直觉设计**：自动补建主账号用的用户名**故意和 seed_test.sql 里的不同**（`autotest_primary_auto` vs `autotest_primary`）。因为预检用"测试库里的 username == 后端登录返回的 username"判断后端有没有连错库 —— 如果补建也用同一个名字，开发库空库自动补建时就会"碰巧对上"，**检查失效**。

## 六、安全测试类（AI 项目尤其加分）

### Q17：越权 / IDOR 怎么测？怎么写才不是"垃圾用例"？

**标准答案**：三个漏洞必须逐个堵。

| 漏洞 | 垃圾写法 | 正确写法 | 本项目位置 |
| --- | --- | --- | --- |
| 只看状态码，不管副作用 | `assert resp.status_code == 403` | 越权后用 owner 视角回查，证明数据**真的没变** | `test_notification_idor.py` 第 1、3 节 |
| 没有正角色对照 | 只有"错角色被拒" | admin / owner 调同样的接口必须 200 | `test_admin_authz.py` 第 6 节、`test_notification_idor.py` 第 5 节 |
| 拿"不存在的 id"当越权样本 | `conversationId: 999999` | 造**真实存在但不属于你**的数据 | `ai_assistant/conftest.py::other_user`、`notification_pair` |

**两个更深的设计点**：
1. **为什么用"管理员读取能力"而不是查数据库来证明"数据没变"**：因为测试库和后端连的库**可能不是同一个**（本项目踩过：后端连 `health_diet`，测试连 `health_diet_test`）。那种情况下查库查出来是 `None`，断言要么崩、要么假绿。改用 admin 的读取能力当证据 —— 走的是同一个后端，物理上不可能对不上。
2. **越权返回 400 而不是 403，是刻意设计**：`test_notification_idor.py` 实测"别人的通知"和"不存在的通知"返回**完全相同**的 `400 {"message":"消息不存在"}`，这是**防枚举**（不能让攻击者通过状态码区分"存在但不是你的"和"不存在"）。第 4 节专门把这条约定钉死 —— 哪天有人"顺手"把越权改成 403，就等于给攻击者送了个用户数据探针。

### Q18：JWT 鉴权怎么测？能覆盖哪些攻击面？

**本项目证据**（`user/test_user_profile.py`）：
- **JWT 篡改三连**：`_tamper_signature`（改签名）、`_tamper_subject`（改 sub 冒充别人）、`_tamper_alg_none`（alg 改成 none，经典的算法降级攻击）。
- **鉴权 6 型**：无 token / 伪 token / 过期 token / 格式错（没有 `Bearer ` 前缀）/ 空串 / 错账号。
- **越权 4 个入口逐个试**：`PROBE_POSITIONS` —— 往 query / header / body / path 里塞别人的 userId，四个入口都不能让你改到别人的数据。

### Q19：测大模型（LLM）接口的自动化，和普通接口有什么本质不同？

这是 AI 项目面试的**必答题**，本项目在这个问题上踩得很深。

**标准答案**：普通接口是"输入 → **固定**输出"，可以断言 `==`。LLM 的输出是**一段自然语言**，同一句问一百次答案都不一样，所以：

> **不能断言"它答得对不对"，只能断言"结构对不对"和"行为对不对"。**

**本项目怎么做分层断言**（这是核心方法论）：

| 层 | 断言方式 | 为什么能精确 | 本项目位置 |
| --- | --- | --- | --- |
| 结构 / 鉴权 / 参数校验 | 精确断言字段 | 确定性 | `test_assistant_结构鉴权.py`（11 条） |
| **代码硬拦**（命中安全规则不调模型） | `blocked == case["blocked"]` + `source == "blocked"` | **不依赖模型**，同一句话问一百次都一样 | `test_assistant_安全拦截.py`（24 条） |
| 意图识别 / 标签 | 弱断言 + pass^k 稳定性 | 有波动，靠多次跑压 | `test_assistant_意图识别.py`（10 条）、`意图标签`（31） |
| RAG 召回 | 金标集 + 召回率 | 检索结果可量化 | `test_assistant_RAG召回.py`（80 条，最大） |

**关键洞察（面试时说出来很亮）**：
> 既然"模型嘴里问不出来的东西"测不准，就**把它搬到"代码里读得出来"的地方**——
> 2026-10-12 后端加了一道**代码硬拦**，命中规则就不调模型、直接返回固定文案。
> 于是 8 条"意图观测不到、断不了"的 skip 有了出路：可以写精确相等、不留余地。

但**代价必须有意识**（这条能显出深度）：
> 这道拦一生效，`test_assistant_意图识别.py` 里「越界-写代码」那条 `pass^5` 哨兵，盯的就不再是"模型守不守规矩"，而是"这几条正则对不对"了。**模型行为那部分从此测不到 —— 换来的是确定性。** 两层是**叠加的，不是替代的**：这里断"没递给模型"，那边断"递过去了它也不照做"。

**`blocked` 和 `source` 两个断言必须合起来看**：
- `blocked` 告诉"拦得对不对（是 medical 还是 out_of_scope）"
- `source == "blocked"` 告诉"**是代码拦的，还是模型自己拒绝的**"
- 这两件事长得像、**修法完全不同**：代码拦住了要改正则（改 Java），模型恰好也拒绝了要改提示词（改字符串）。只断 `blocked` 的话，哪天有人把拦截挪回模型侧，用例照样绿。

### Q20：AI 助手怎么测安全（越狱 / 注入 / 系统提示词泄露）？

**本项目证据**（`test_cases/ai_assistant/`，数据在 `data/assistant_*_cases.yaml`）：

| 文件 | 条数 | 测什么 |
| --- | --- | --- |
| `test_assistant_越狱.py` | 21 | 红队对抗样本，算**攻破率**并导出 Excel 报告 |
| `test_assistant_注入.py` | 13 | 提示词注入（"忽略前面的指令"之类） |
| `test_assistant_越权.py` | 5 | A 能不能读 B 的会话 |
| `test_assistant_上下文.py` | 5 | 多轮上下文保持 |
| `test_assistant_通用问题不追问档案.py` | 3 | 问"1+1"不该追问健康档案 |
| `test_assistant_安全拦截.py` | 24 | 代码硬拦，含 **"误伤回归-*"** 那批（当时"期望放过、实际被拦"的样本，规则修好后转正成回归用例） |

**两个方法论**：
1. **一定要配"误拦率"反向用例**。只测"该拦的拦住了"，正则收紧到最严就全绿 —— 但正常用户会被拦死。`PASS_CASES` 这批就是守这个的。
2. **"期望值全部来自实测，不是照抄规则"**。先用探针跑一遍规则，看实际拦不拦；规则改了以实测为准。

**评测留痕是旁路**（`common/eval_record.py` + `eval_record.observe()`）：每次问答把 `intent / source / blocked / 回答全文` 存一份，跑完落 `tools/eval/eval_results.json`，再由 `eval_runner.py` 离线算指标（**改口径不重跑模型**）。放 `ask` 夹具里而不是各用例里，一处埋点覆盖全部。
> ⚠️ 只在**真的采到观测**时才写 —— 跑一批非 AI 用例（0 次模型调用）不该把上一份完整评测数据覆盖成空。

## 七、报告与日志类

### Q21：Allure 怎么集成？为什么说"报告必须走旁路"？

**本项目证据**（`common/allure_helper.py` + README 约定 12）：

| 决定 | 理由 |
| --- | --- |
| **请求/响应请求自动贴成附件** | 在 `base_api_client._log()` 一处埋点，全场覆盖，用例一行不用改 |
| **`--alluredir` 不写在 `pytest.ini` 里** | ① 相对路径按**当前工作目录**解析，PyCharm 里换工作目录就写到别处去了；② 没装 `allure-pytest` 的机器上会报 `unrecognized arguments`，**全场用例一条都跑不起来** —— 一个可选的报告不该有这种杀伤力 |
| **必须 `tryfirst` 挂 `pytest_configure`** | 要在 **allure 自己的 pytest_configure 之前**把目录塞进选项（allure-pytest 读的是当时的选项值） |
| **`Authorization` / `password` 默认打码** | 报告是被转发的 HTML，明文摊进去 = 泄露凭据 |
| **截断 2 万字符** | SSE 和大响应体不截断能把报告干到几百 MB |
| **不许用例里自己 `import allure` 贴东西** | 用例各贴各的，就会出现"有的用例有附件、有的没有"，报告的价值立刻塌一半 |
| **加任何报告层的东西之前先问：它挂了会不会把绿的用例搞红？** | **观测工具不该成为被测对象** |

**还有一个坑**：**别在埋点里读不该读的东西** —— 对 `stream=True` 的响应调 `resp.text` 会把整条流读干，`test_assistant_流式.py` 当场挂。判据是"贴给报告的内容，必须是本来就该读、且读一次没关系的东西"。

### Q22：日志怎么设计？（这一项其实也考**输出设计能力**）

**本项目证据**（`common/logger.py` + `conftest.py`）：

- **控制台**：每条用例一个边界框（`┌─ ▶` / `│` 前缀 / `└─ ✔ PASSED`），完整响应体默认不刷屏、失败时由 pytest 自动展开。
- **文件**：`logs/runs/run-YYYY-MM-DD_HHMMSS.log` 每轮一个，内容完整（含全部响应体）；`logs/latest.log` 指向最近一次。
- **日志排版三原则**：① 前缀只留必须的（日期在同一份文件里重复几十遍，纯噪音）；② 变的放后面、固定列对齐；③ 一行一条。
- **只有 5xx 才是 WARNING**：400 是我们主动测出来的正常剧情，全标成警告的话警告就泛滥成噪音、失去"一眼挑出问题"的作用。

**踩过的两个坑**：
1. **pytest 会捕获 stdout**，直接写终端的日志会被吞掉 → 每条记录写入前 `suspend_global_capture()`、写完 `resume_global_capture()`；不挂起还会和下一条输出缓冲错位（两行挤在同一行）。
2. **`--no-summary`**（PyCharm 默认就带 `--no-header --no-summary -q`）会让 pytest **整个跳过** `pytest_terminal_summary`。所以总账不能只写在那里 —— 必须同时（甚至主要）放在 `pytest_sessionfinish`，那个钩子不受此开关影响。

### Q23：统计口径有什么坑？

**本项目证据**（`conftest.py::_collect_summary`）：

> **必须按 nodeid 归并三个阶段（setup / call / teardown）的报告，不能直接数 report。**
> 一条用例可能 call 通过、teardown 报错（典型：越权用例的清理失败），在 stats 里会同时占 `passed` 和 `error` 两条 —— 直接相加，216 条用例会算成 221 条，**总数从此不可信**。

归并规则：
- call 通过 + teardown 报错 → **算 error**（清场没做干净不能报绿）
- call 失败 → failed
- call 跳过 + 有 `wasxfail` → **xfailed**（≠ skipped）
- 没有 call 报告 → setup 挂了算 error，否则 skipped

耗时按模块累加**三条** report —— 只算 call 会漏掉夹具里登录、清场的时间，而那部分往往比用例本身还久。

### Q25：文档漂移怎么防？

**标准答案**：**数字靠手工同步一定会漂，必须用脚本校验**。

**本项目证据**：这一点本项目**吃过两次**：
1. README / 覆盖矩阵 / 缺口清单三份文档的数字从 98 → 181 → 293 → 346 → 386 一路手工维护，2026-10-23 和 10-26 各同步了一次。
2. **本次实测又漂了**（见 §九）：文档写 386 / 346，实际 387；文档写 smoke 118 / p0 149 / p1 197，实际 158 / 189 / 198。

缺口清单 P0-6 里其实已经写了正确解法："**建议加 `tools/doc_stats.py` 并在 CI 对比**" —— 但还没做。面试时把它当成"我知道问题在哪、也知道怎么解，只是还没排上"，是加分不是减分。

### Q26：接口覆盖率怎么算才不算自欺欺人？

**本项目证据**：
- 后端控制器方法级 **78** 个接口，已覆盖 **23** 个 ≈ **29.5%**。
- ⚠️ **这 23 个里有 5 个只覆盖了"能不能进"，没覆盖"进去之后对不对"**（`/admin/overview`、`/user/admin/list`、`/user/admin/{id}/status`、`/article/admin/collect-stats`、`/notification/admin/publish`）。
  > **统计上算覆盖，但别把它们当成"业务已验证"。**

**这个"给自己扣分"的口径值得学**：覆盖率这个数字最容易骗自己 —— 打了一次接口就标 ✅，和"验了业务语义"是两回事。

### Q27：怎么判断一个发现是"缺陷"还是"观察点"？

**本项目最反直觉的一条纪律**（README 约定 9）：

> 报缺陷之前，先回答一句：**"我说'应该这样'，依据是什么？"**
> 依据只能是三者之一：① 文档/需求/前端页面写明了的 ② 表结构、字段语义明确表达的 ③ 团队已经按某个标准修过同类问题（先例）。
> 三者都不是 → 记成「**观察点**」，**别写进缺陷单**。判缺陷用的是**需求**这把尺子，不是"我的直觉"。

**反面教材（本项目自己踩的）**：把"`PUT /user/profile` 传 `email` 不生效"报成缺陷 —— 可前端编辑个人资料页**根本没有邮箱输入框**，需求里就没这个功能。同一把尺子还砍掉了"`phone` 可以重复"（文档只要求用户名/邮箱查重）。

**还有一条**（缺陷 #11 学到的）：**"写用例就是在定契约"**。修 `phone` 空串行为时一度放开成"解绑"，结果和 `test_update_profile_fail[空串]` 那条用例断言"空串应被拒"直接撞车。`""` **不能既是"非法输入"又是"解绑指令"** —— 最后按用例的契约回退成 400。**改行为前先看一眼有没有用例守着**。

## 十、如果只能准备三句话（电梯陈述）

1. **分层让它可维护**：用例里没有 URL，改一个接口只动 `api/` 里一行；断言有三把尺子（成功 / 业务失败 / 权限拒绝），因为它们对应三套不同的响应体系。
2. **防假绿是主线**：模型不可用时后端仍返回 200、越权只断 403 没有正角色对照、越权样本用不存在的 id、契约层自己有 bug —— 这四类假绿本项目都专门堵过，`contract/test_契约层_自测.py` 那 28 条就是"测试的测试"。
3. **LLM 测试只能断结构和行为，不能断内容**：确定性靠"代码硬拦"搬到能被精确断言的地方，波动部分靠分层（smoke/p0/p1）和 pass^k 压住；而且要接受代价 —— 硬拦一生效，模型行为那部分就测不到了，两层是叠加不是替代。
