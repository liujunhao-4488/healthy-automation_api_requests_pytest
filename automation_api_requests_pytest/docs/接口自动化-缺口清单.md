# 接口自动化框架 · 缺口清单

> 编写日期：2026-10-23
> 评估对象：`automation_api_requests_pytest`（pytest + requests）
> 评估口径：对照"标准接口自动化框架"应具备的 12 项能力——配置管理、用例分层、请求封装、断言/契约、数据驱动、数据生命周期、日志、报告、环境管理、Mock/故障注入、CI/CD、质量门禁。

## 一、结论

框架的**结构层**已经达标：分层清晰、请求封装收敛、数据驱动完整、DB 校验与清理、日志与 Allure 旁路、xfail/XPASS 缺陷固化，这些在多数团队里都算做得好的部分。

真正的缺口集中在三件事：

1. **可复现**——已补基础版：独立测试库 + 一键建库 + 账号自愈 + 环境预检（2026-10-23）。剩余：CI 中 MySQL 服务的编排；
2. **可进 CI**——没有流水线、没有用例分层、依赖未锁版本；
3. **断言够硬**——只校验 HTTP 200 + 业务 code，没有契约/字段级校验。

## 五、P1：可靠性与执行效率

### P1-1 每条用例都重新登录（已补 · 2026-10-23）

| 项 | 内容 |
| --- | --- |
| 原现状 | `conftest.py` 的 `token` 是函数级 fixture，293 条用例 = 293 次登录 |
| 影响 | 执行时间被登录请求吃掉；后端压力无谓增加 |
| 已实现 | ① `api` 改为 session 级，新增 session 级 `_auth_state`：整场只调用一次 `ensure_primary_account()`；<br>② `token` / `auth_headers` 仍是 function 级，只从 `_auth_state` 取**当前** token，用例一行不用改；<br>③ `BaseApiClient` 增加 401 钩子：**仅当请求带的是当前会话 token** 时才重登并重发一次；不带 token / 伪 token / 别人的 token 的负向 401 原样返回，不会被“重登”洗成 200 |
| 登录次数 | 测试会话：**1 次**（原先 293 次）；环境预检的账号保障请求不计入用例登录 |
| 验证 | ① 当时 `--collect-only` 收集 293 条（现 346 条）；② 本地假服务自测通过：旧 token → 401 → 自动重登 → 200，伪 token 保持 401，关闭钩子后不再重试。**真实后端全量未跑（8080 / 5000 未启动）** |
| 验收标准 | 全套用例登录次数 ≤ 2 次，执行时间明显下降 |

### P1-2 无并行、无重试、无用例级超时（已补 · 2026-10-26）

| 项 | 内容 |
| --- | --- |
| 原现状 | 单进程串行；`requirements.txt` 无 xdist / rerunfailures / timeout |
| 已实现 | ① 安装 `pytest-xdist 3.8` / `pytest-rerunfailures 16.7` / `pytest-timeout 2.4`，并写进 `requirements.txt`；<br>② `pytest.ini` 配 `timeout = 180`（整条用例，含 setup/teardown）；<br>③ 重试只认网络类失败：`reruns = 2` + `only_rerun` 匹配 `ConnectionError / ReadTimeout / ConnectTimeout / Max retries exceeded / Connection reset`，断言失败不重试；<br>④ xdist 采用**显式开启**：`pytest -n 4 --dist=loadscope`；controller 统一做一次环境预检，worker 跳过；worker 不写评测留痕/Allure 环境文件（避免互相覆盖）；<br>⑤ `common/db.py` 无需改：xdist 是**多进程**，模块级连接天然是每 worker 一份 |
| 限制 | ① 4 worker 并行通过率**未实测**（8080 / 5000 未启动）；<br>② AI 评测留痕必须串行（观测是进程内内存，worker 之间无法合并）；<br>③ xdist 下每个 worker 各登录一次（P1-1 的“≤2 次”只对串行成立）；<br>④ Windows 的 timeout 走 thread，杀不掉卡死线程，超时会 dump 栈并终止整场；Linux/CI 的 signal 才能“单条独立失败” |
| 验证 | ① 三个插件正常加载，当时 `--collect-only` 串行 / `-n 2` 均收集 293 条（现 346 条）；<br>② 本地自测：抛 `ConnectionError` 的用例重跑 2 次（`2 rerun`），断言失败只跑 1 次；<br>③ 超时配置可被 `-o timeout=2` 覆盖并触发（Windows 表现为整场中止） |
| 验收标准 | 4 worker 并行通过率与串行一致；单条用例超时能独立失败（Windows 除外） |

### P2-1 断言只到"成功/失败"（部分补 · 2026-10-26）

| --- | --- |
| 原现状 | `assert_ok` 只校验 HTTP 200 + `code == 200`；错误场景 60+ 处手写三层断言 |
| 已实现 | ① `assert_ok` 增加“响应必须是 JSON 对象”+ 可选 `schema=`（JSON Schema draft-07，`jsonschema` 已进 requirements）；<br>② 新增 `assert_error`：HTTP + 业务 code + 文案，默认精确相等，兼容 401 空体；已在 auth / health / user / assistant 使用 15 处（参数化后覆盖的失败例更多）；<br>③ 新增 4 个契约文件（24 条）+ 断言层自测（28 条）；注册成功响应已接 `REGISTER_SCHEMA`；<br>④ 断言层自测纳入 `smoke` 分层 |
| 剩余 | ① 15 个已覆盖接口里还有 3 个成功出口没接 schema：`POST /health/goal`、`POST /assistant/conversations`、`DELETE /assistant/conversations/{id}`（`/assistant/chat/stream` 是 SSE，不适用 JSON Schema）；<br>② 仍有约 2 处手写三层（assistant 结构鉴权）+ 若干 401 单行断言；<br>③ `ok()` 不禁止额外字段（未设 `additionalProperties: false`），“字段变多”不会红 |
| 验证 | 全量 346 条收集通过；`schema=` 10 处、`assert_error` 15 处（不含 28 条自测）；契约自测在无服务环境下会被预检拦住，尚未实跑 |
| 验收标准 | 核心接口全部有 Schema 校验；失败用例统一走 `assert_error` |

### P2-2 无契约测试（部分补 · 2026-10-26）

| 已实现 | ① `common/schemas.py`：9 份 draft-07 schema（LOGIN/REGISTER、PROFILE、HEALTH_INFO/HISTORY/GOAL、CHAT、CONVERSATION_LIST、MESSAGE_LIST）；<br>② 4 个契约文件 24 条（auth 4 / user 4 / health 9 / assistant 7）+ 断言层自测 28 条；<br>③ schema 校验接入 `assert_ok`，失败用例统一走 `assert_error` |

## 八、暂不建议做

- 不引入 HttpRunner / 商业测试平台：当前 pytest 骨架已经覆盖其核心能力，迁移成本大于收益。
- 不在用例里断言响应耗时：延迟波动会造成随机红；性能指标继续走 `tools/latency_report.py`，只在独立性能任务里设阈值。
- 不为了覆盖率硬凑接口：优先补 P0 越权与核心写接口，低频管理接口可延后。
