# 1. 请求链路：一条用例跑起来，中间经过谁

## 七个站点

```
pytest.ini            →  告诉 pytest 去哪找用例、日志怎么显示
  ↓
test_login.py         →  用例本体：只写「业务」，不写 URL
  ↓
conftest.py           →  夹具：api / token / auth_headers
  ↓
api/__init__.py       →  总入口 Api：把各接口模块挂在自己身上
  ↓
api/auth_api.py       →  唯一写 URL 的地方
  ↓
api/base_api_client.py→  底座：发请求、记日志、断言
  ↓
config/config.py      →  BASE_URL / TIMEOUT / 账号 / 数据库参数
```

## 为什么要分这么多层

**一句话：让「业务」和「实现细节」分开，各自改各自的。**

- 接口路径变了 → 只改 `api/auth_api.py`，**用例一个字不动**
- 环境地址变了 → 只改 `config/config.py`
- 用例只关心「登录失败了应该返回什么」，不关心 `/auth/login` 长什么样

## 关键设计：`Api` 故意不继承 `BaseApiClient`

```python
# api/__init__.py
class Api:
    def __init__(self):
        self.auth = AuthApi()
        self.user = UserApi()
        self.health = HealthApi()
```

不让 `Api` 继承底座，是为了**从结构上堵死 URL 泄漏**：

- 如果继承了 → 用例里写 `api.post("/随便什么路径")` **也能跑通**，URL 就又多了一条偷偷漏回用例的路，**而且不报错，很难发现**
- 现在不继承 → 写 `api.post("/x")` 直接 `AttributeError`，**路径想漏都漏不出去**

> **这条防线是「结构上不给」，比「约定上不写」硬。**

## 面试答法

> 「我的框架分三层：**接口封装层、公共层、用例层**。用例里只写业务语义，比如 `api.auth.login(data)`，**不出现任何 URL**——URL 全部集中在 `api/auth_api.py`。这样接口路径改了只改一个文件，用例完全不用动。还有一点：我的总入口 `Api` **故意不继承**底座的请求方法，这样谁想在用例里直接 `api.post('/xxx')` 会直接报错，**结构上就不可能把 URL 写回用例里**。」

# 2. `Session` 的坑（面试爱问）

```python
def __init__(self):
    self._session = requests.Session()
    self._session.headers.update({"Content-Type": "application/json"})
```

## Session 是什么

一次会话，会**持续保存 cookie 和 headers**，并复用同一条 TCP 连接（keep-alive）。
跑几百条用例时不用反复握手，这是用它的主要原因。

## 坑在哪

Session 是**有状态**的。如果在某个方法里写：

```python
self._session.headers.update({"X-Trace": ...})   # ← 危险
```

**后面所有请求都会带上这个头**，你还不一定记得设过。

## 为什么我的代码是安全的

两个原因：

1. headers **只在 `__init__` 设了一次**，没有任何方法中途改它
2. `api` fixture **没指定 scope → 默认 function 作用域**，所以**每条用例都 new 一个 `Api()`，也就是 new 一个 Session**

## 什么情况下会出事

把 fixture 改成 `@pytest.fixture(scope="session")`，整个测试会话共用一个 `Api`
→ 一条用例设的 header 就会**污染后面所有用例**。

## 面试答法

> 「Session 复用 TCP 连接、保存 cookie 和 headers。风险是它**有状态**——一旦在请求过程中改了 headers，会泄漏到后续请求。所以我把 Session 的创建放在 `__init__`，并且 fixture 用默认的 function 作用域，**每条用例一个新 Session**，隔离掉这个风险。」

# 3. `data_loader.py` —— 四种格式 + 两个坑

## 目标一句话

让用例**只拿 `list[dict]`**，不关心数据来自哪个文件、什么格式。
所以 `data/` 下有 `login_cases.json` / `.csv` / `.yaml` / `.xlsx` 四个孪生文件——
**换格式只改用例里那一行文件名**，代码一个字不动。

## 坑 1：CSV 读出来全是字符串

`csv.DictReader` 不知道类型，`200` 会读成 `"200"`。
这时 `assert resp.status_code == case["want_http"]` 会挂——**`200 != "200"`**。

所以有了 `int_fields` 参数：

```python
CASES = load_cases("login_cases.csv", int_fields=("want_http", "want_code"))
```

**这就是为什么 YAML/JSON 更好用**——它们自带类型，数字就是数字。

## 坑 2：Excel 存 CSV 的 BOM

```python
for enc in ("utf-8-sig", "gbk"):
```

中文 Windows 上 Excel 存的 CSV 有两个经典坑：

- **UTF-8 带 BOM**：文件头多出 `﻿`，第一列列名变成 `"﻿name"`，按 `row["name"]` 取就 KeyError
- **GBK/ANSI**：压根不是 UTF-8，直接 UnicodeDecodeError

`utf-8-sig` 会**自动吃掉 BOM**（没 BOM 时也正常工作），失败再退回 `gbk`。
这是读「别人给的数据文件」的标准防御姿势。

## 附带的小设计

`_read_excel` 里跳过**全空行**——Excel 表格底部常有一堆「幽灵行」，
不跳过就会多出几十条空用例。

## 面试答法

> 「数据驱动我用统一的 `load_cases()` 收口，支持 json/csv/yaml/xlsx，用例只拿到 `list[dict]`。踩过两个坑：CSV 读出来全是字符串，`200` 会变成 `'200'`，所以加了 `int_fields` 做类型转换；还有 Excel 存的 CSV 带 BOM，第一列列名会多出 `﻿`，用 `utf-8-sig` 解决，并用 `gbk` 兜底。」

# 4. `logger.py` —— 日志为什么会打两遍（经典坑）

## 根因：Python logging 是树形结构，日志会「冒泡」

```
autotest (子 logger)
    ↓ 自动向上冒泡
root (根 logger)  ← handler 挂在这里
```

在 `autotest` 上 `log.info(...)`，这条记录会**自动冒泡到 root**，然后被 root 上的 handler 写一次。

**如果给 `autotest` 自己再加一个 handler** → 同一条日志被两个 handler 各处理一次 → **打两遍**。

所以代码里这个做法是对的：

```python
root = logging.getLogger()
root.addHandler(fh)        # ← 只挂 root，且用 _ready 保证只装一次
```

> **千万别再给 logger 自己额外加 handler。**

## 第二个设计：`_IN_PYTEST = "pytest" in sys.modules`

- 是 pytest 跑 → 控制台显示交给 `pytest.ini` 的 `log_cli`，logger **只写文件**
- 是独立脚本（`python xxx.py`）→ 没人替你显示，自己补一个 `StreamHandler`

## 第三个亮点：`_display_width()`

用 `unicodedata.east_asian_width` 算显示宽度。

因为 `len("密码错误")` 是 **4**，但在终端里占 **8 列**——
直接用 `ljust` 对齐，中英文混排的列会**参差不齐**。这个细节很少有人想到。

## 面试答法

> 「日志我挂在 **root logger** 上，因为 Python logging 是树形结构，子 logger 的记录会冒泡到 root，挂一处就能收全所有模块的日志。这里有个坑：**不能给子 logger 自己再加 handler**，否则同一条日志会被写两遍——冒泡和自处理会各来一次。另外我做了 pytest 环境判断：pytest 里控制台交给 `log_cli`，我只写文件，避免重复输出。」

# 5. `db.py` —— 连接复用与事务

## ① 连接复用

```python
_conn = None
_IDLE_BEFORE_PING = 30.0

def get_conn():
    if _conn is None:
        _conn = pymysql.connect(**DB, autocommit=True)
    elif now - _last_used > _IDLE_BEFORE_PING:
        _conn.ping(reconnect=True)     # 探活
```

- **缓存一条连接**，省掉每次 TCP + 认证握手的开销
- **不是每次都 ping**，而是闲置超过 30 秒才 ping——ping 本身要走一个来回，每次都做等于白费
- `ping(reconnect=True)`：MySQL 服务端有 `wait_timeout`，闲置久了会**单方面断开**，ping 探活能悄悄重连

**代价（这点面试要主动说）**：连接**是有状态的**，多线程并发共用会串味。
所以它安全的前提是——**pytest 是单进程顺序跑的**。

## ② 事务

```python
def transaction():
    conn.begin()          # 显式开事务，autocommit 被挂起
    try:
        yield cur
    except Exception:
        conn.rollback()   # 出事自动撤销
        raise
    else:
        conn.commit()
```

解决什么问题：「造数据 → 验证 → 清理」这个套路里，**清理最容易忘**。
交给事务，就算用例中途挂了，数据也不会留在地上。

## ③ 日志的一个巧思

写操作用 `WARNING` 级别，读用 `INFO`：

```python
log.info("· READ  ...")        # · 只读
log.warning("! WRITE ...")     # ! 写 —— 一眼看出「谁动了数据」
```

跑测试时翻滚的日志里，写操作会**自己跳出来**。这是安全意识落到了实现里。

## 面试答法

> 「数据库工具做了三件事：**连接复用**（模块级缓存 + 闲置 30 秒才 ping，避免每次握手）；**能写**（execute / executemany）；**事务**（上下文管理器，异常自动回滚，解决『造数据忘了清理』的问题）。有个前提必须说明——连接是有状态的，所以只在单进程顺序跑的 pytest 里安全，**多线程并发会有问题**。」

# 6. `yield` 夹具 —— 夹具被劈成两半

```python
@pytest.fixture
def temp_user(api):
    # ① yield 之前 = setup：造人
    body = api.assert_ok(api.auth.register(data), "注册靶子账号应成功")
    user = {...}
    yield user                      # ← 把 user 交给用例，用例从这里开始跑

    # ② yield 之后 = teardown：拆人
    db.execute("DELETE FROM `user` WHERE email = %s", (user["email"],))
```

## 最关键的一点

pytest 调用夹具时，会在 `yield` 那里**挂起**，跑到用例里去；用例结束后再**回到 yield 后面**继续执行。

而且——**它是用 `try / finally` 包起来的**。所以：

> 用例断言挂了、代码抛异常了，`yield` 后面的清理**照样执行**。

这就是为什么「造临时账号」不用担心中途失败会留下垃圾账号。

## 为什么不能用 `return`

因为 `return` 之后函数就结束了，后面的清理代码**永远执行不到**。
这就是 yield 夹具存在的全部理由。

## 面试答法

> 「yield 夹具是 pytest 做 setup/teardown 的标准写法。yield 之前造数据，之后清理。它的保证是——pytest 内部用 try/finally 包住，所以**用例失败也会执行清理**。用 return 就交不出清理逻辑了。」

# 7. 为什么不用张三？（这题答得好非常加分）

```python
# 造一个临时靶子账号，供 PUT 用例改；用例跑完从库里删掉。
```

**表面理由**：PUT 是写操作，会把张三的档案真改掉。

**但真正的理由更狠**——这两条失败用例：

- 用户名已存在
- 手机号已被使用

**在一个「自己」的账号上提交，这两条根本测不出来。**
后端判重时会发现「这就是你自己啊」，于是放过你 → 返回 200 → 用例**假失败**。

**必须用一个「别人」的身份去提交，判重才会真的拦下来。**

## 面试答法

> 「改资料的用例我用一个临时注册的靶子账号，跑完删掉。除了不污染主账号，还有个更重要的原因——测『用户名已存在』『手机号已被使用』这类判重逻辑，**必须站在别的账号上提交**。用自己的账号提交，后端判重会放过『自己』，根本触发不到 400。**测判重，需要一个不是自己的身份。**」

# 8. 双重验证：不只看响应，还要查库

```python
body = api.assert_ok(resp, "改用户名应成功")
assert body["data"]["username"] == new_name        # ← 接口说它改了

# 不只信响应，去库里核对（接口 + DB 双重验证）
row = db.query("SELECT username, email, phone, avatar FROM `user` WHERE email = %s", ...)
assert row["username"] == new_name                 # ← 库里证明它真的改了
```

## 为什么两遍都要

因为这是**两个不同的断言**：

| 断言 | 证明的是什么 |
|---|---|
| 响应 `data.username == new_name` | 接口**说**它改了（只证明了出参） |
| 库里 `username == new_name` | 接口**真的**改了（证明了落库） |

**中间可能断链**：接口返回新名字，但 Service 层忘了调 `updateById` → 数据库里还是旧的。
**只断响应，这个 bug 永远抓不到。**

## 还有两条更细的

```python
assert row["phone"] is None, "没提交 phone，就应保持原样（这里是 null）"
```

这是**局部更新（partial update）** 的验收：传了 `{"username": "x"}`，没传的字段**不能被清空**。
很多系统的 bug 就出在这——`updateById` 把没传的字段一起写成 null 了。

```python
assert data["role"] == "user", "role 不该被改成 admin"
```

这是**越权**的一条：`email / role / status / userId` 传了也没用，静默忽略。
**如果这些字段真能被改，用户就能把自己改成管理员。** 这是安全测试的落地。

## 面试答法

> 「写接口我断言两遍：一遍断响应体，一遍去数据库 SELECT 核对。因为**响应只证明接口说它改了，DB 才证明它真的改了**——中间 Service 层漏调更新是抓不到的。另外我专门测了局部更新：没提交的字段不能被清空，还测了 role / status 这类只读字段必须被忽略，防止越权把自己改成 admin。」

# 9. `_free_phone()` —— 一个小函数，一个大坑

```python
"""为什么要动态找？实测发现所谓的"经典测试号"13800138000 **真的被占用了**
（库里 id=100182 正在用）。写死任何号码都可能某天撞车 → 用例假红。"""
```

这段注释是**整个项目里最值钱的一段**。

**它记录的是一次真实踩坑**：随手写了个「经典测试号」，以为够用了 ——
结果**它真的被别人占了**。用例从此就红着，你还以为是代码问题，查半天才发现是数据冲突。

**解法**：现查现用 —— 随机生成一个号，`SELECT COUNT(*)` 查库确认没人用，再用。
查 20 次都不行就明确抛错。

## 这个坑的通用形式叫「假红」（false failure）

> **用例失败的原因不是程序有 bug，而是测试数据变了。**

## 面试答法

> 「我踩过一个坑：写死了测试手机号 13800138000，结果库里真的有人占用了，用例一直红。后来改成**动态找空闲号**——随机生成后查库确认没用过再用。这属于『**假红**』：失败不是代码的问题，是测试数据的问题。所以**写死的数据越少越好**，尤其是别人可能也在用的测试环境。」

# 10. `xfail` 钉缺陷（很高级的一手）

```python
@pytest.mark.xfail(reason="已知缺陷：PUT /user/profile 不刷新 update_time", strict=True)
def test_update_profile_refreshes_update_time(api, temp_user):
    ...
```

## `xfail` 是什么

**「我知道这条会失败，是预期内的。」**
跑出来结果不是红，而是 **XFAIL**（黄色）。测试套件整体还是绿的。

## 为什么不干脆把这条用例删了

- **删了 = 缺陷失忆**。三个月后没人记得这里有个 bug
- **留着 = 缺陷有据可查**，而且哪天修好了，套件会**自动告诉你**

## `strict=True` 是精髓

| 情况 | 结果 |
|---|---|
| 现在跑（还没修） | XFAIL —— 正常 |
| 后端修好了 | **XPASS** → `strict=True` 把它**判成 FAILED** |

**为什么修好了反而失败？** 因为这是在提醒你：
**「这个缺陷已经不存在了，把 xfail 标记摘掉，改成正常用例。」**

## 面试答法

> 「已知缺陷我用 `xfail` 钉住，不用删也不用注释掉。好处是缺陷在代码里有记录，不会失忆。关键是 **`strict=True`**——哪天后端悄悄修好了，用例会变成 XPASS，strict 模式把它判成失败，**强制我们去摘标记、转成正式用例**。这样缺陷的整个生命周期都是可追踪的。」

# 11. `data_factory.py` —— 大量数据靠「生成」不靠「手写」

```python
"""手写 1000 条数据是灾难；写 10 行生成逻辑，就能产出成千上万条数据，
而且**可复现**（固定随机种子 → 每次生成同一批 → 失败能重跑定位）。"""
```

## 四个函数对应四种测试设计方法

| 函数 | 干什么 | 对应的方法论 |
|---|---|---|
| `cartesian()` | 各维度取值全组合 | **全组合测试**（笛卡尔积） |
| `boundary_numbers([6, 50])` → `[5,6,7,49,50,51]` | 关键值 ±1 | **边界值分析法**（错误常藏在边界） |
| `lengths([0, 5, 6])` → `["", "aaaaa", "aaaaaa"]` | 长度样本 | 等价类 / 边界，用于字符串长度 |
| `fuzz_emails()` | 从畸形片段池拼邮箱 | **Fuzz 健壮性测试** |

## `seed=42` 是关键细节

```python
rng = random.Random(seed)   # 固定种子 → 每次生成同一批数据
```

**为什么要固定种子？** 因为**随机数据必须可复现**。
如果每次跑都生成不一样的数据，一条用例失败了，你**没法重跑定位**。
固定种子让「随机」变成「看起来随机但每次都一样」。

## `fuzz_emails` 的片段池值得看

```python
fragments = [" ", "@", "@.", "..", "a@@b", "测试@", "<x>", "'; --", "a@b@c", "%00"]
```

注意最后两个：`'; --`（**SQL 注入**）和 `%00`（**空字节截断**）。
这不是随便凑的——**这是在拿畸形输入探接口会不会 500**。
**接口对垃圾输入必须稳定地返回 400，而不是崩掉。**

## 面试答法

> 「数据驱动有两种来源：**数据文件**（json/csv/yaml/xlsx，适合固定用例）和**数据工厂**（代码生成，适合大批量）。数据工厂里我用了笛卡尔积做全组合、边界值分析法生成 ±1 的边界点、还有 fuzz 生成畸形邮箱——片段池里特意放了 `'; --` 和 `%00` 这类注入特征，验证接口稳定拒绝、不返回 500。所有随机都**固定种子**，保证可复现——不然失败了没法重跑。」
