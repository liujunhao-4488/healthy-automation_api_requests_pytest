## 四、写用例前必须确认的 3 个环境事实

> 这三条来自 API.md §15，**不确认就写用例，会写出"假红"**。

1. **推荐类接口依赖算法服务**：`/recommend/*`、部分 `/record/suggestions` 需要 Flask 服务在 `localhost:5000` 跑着，否则接口会失败——**这不是被测系统的 bug**。
2. ~~**管理员接口的拒绝方式不唯一**：API.md 说"返回 403 或业务 400"，所以断言写 `in (403, 400)`。~~
   **❌ 2026-10-28 实测更正：5 个管理接口、每种非法身份，全部是纯 403，一次 400 都没有。**
   原因：Spring Security 在**进业务层之前**就拦了，业务层那段 `requireAdmin()` 根本没机会执行。
   所以：
   - 断言可以直接写死 `== 403`，不需要 `in (403, 400)` —— 写宽了反而会让"某天 403 退化成 400"这种
     鉴权降级悄悄溜过去。
   - 403 的响应体是 **Spring 默认错误体** `{timestamp, status, error, path}`，**不是**统一信封
     `{code, message}`（缺陷 #10）。所以它**不能**用 `assert_error`，要用 `assert_forbidden`。
   - 401 全站都是**空响应体**，也不能 `resp.json()`。

3. **`/recipe/*` 的认证声明与实际不符**（已实测）：文档写 `list` / `detail` / `search` / `nutrition` / `recommend` 是"无需认证"，但实测 **无 token → 401**。写用例时以**实测结果**为准，并记入缺陷单。

### ⚠️ 判定纪律：缺陷 = **与需求/设计不一致**，不是"与我的直觉不一致"

列进上表之前，先回答一个问题：**"应该这样"这句话，依据是什么？**
依据必须是下面之一，否则降级到「观察点」，别急着报 bug：

1. `API.md` / 前端页面 / 产品需求里**写明了的**；
2. 表结构、字段语义**明确表达的**（如 `update_time` 带 `ON UPDATE CURRENT_TIMESTAMP`）；
3. 团队**已经按某个标准修过同类问题**（先例）。

反面教材：我 2026-09-30 探测 `/user/profile` 时，把"传 `email` 不生效""`phone` 可以重复"直接写成了缺陷 #11/#12，
**却没回头核对需求** —— 前端编辑个人资料页根本没有邮箱输入框、`API.md` 只声明可改「用户名/手机号/头像」，
注册校验也只写了「用户名/邮箱查重」。两条都是**设计如此**，被我误判成 bug。

**这条纪律没被推翻，后续把完整流程走完了（同一天）**：

`phone` 重复先降级到观察点 **O2**（"设计如此"），用户确认"手机号必须唯一"之后——
它**从"设计如此"升级成"需求变更"**，于是按变更实现（缺陷 **#11**，已修复）。
所以正确姿势不是"别报"，而是**先确认、再定性**：

| 阶段 | 定性 | 该写在哪 |
|:--|:--|:--|
| 只看到"两个账号手机号相同" | 观察点（可能设计如此） | 观察点表（O2） |

### 附带教训：缺陷修好了，用例却"假失败"——撞秒

`test_bug_update_time_not_refreshed` 断言的是 `after != before`，
而 `updateTime` 精度只到**秒**。文件级/全套连续跑时，**前一条用例的 teardown 还原**
和本用例的写入会落在同一秒，`after == before` → 断言失败 → 记成 XFAIL。
后端此时已经是好的，是**用例写法**制造了假失败。

**实测证据**：单独跑这条用例 6/6 通过（XPASS）；整个文件连着跑 4/4 失败（XFAIL）。

> 教训：断言"某字段变了"时，先看它的**时间精度**够不够分辨两次写操作；
> 不够的话，要么跨秒（`time.sleep(1.1)`），要么改判更有意义的东西——
> "这个时间戳是不是刷新成了刚才那一刻"。
> 完整改写代码见 `README.md` 第六节末尾。
