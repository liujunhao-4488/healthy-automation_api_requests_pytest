>
> ⚠️ **子类方法禁止叫 `get` / `post` / `put` / `delete`** —— 那会覆盖底座发请求的四个方法，
> 然后 `self.delete(...)` 无限递归，报 RecursionError 跟业务毫无关系。所以删记录叫
> `delete_record`、列表叫 `list_all` / `list_records` 而不是 `list`（后者会遮住内置 list）。
> 这条 2026-11-06 写 record_api 时差点踩到，记在这里。
>
> **补新接口时的顺序**：先往 `api/<模块>_api.py` 加方法 → 再写用例 → 回来把矩阵 ⬜ 改 ✅。
> 用例里直接写 URL（`api.get("/xxx")`）已经不行了 —— `Api` 类**故意不提供** `get/post/...`，
> 详见 README 第五节约定 10。

## 三、优先级小结（按“回归价值”分档）

> 2026-11-06 重排：旧版按“开工顺序”排 P0/P1/P2，容易滑成“为了覆盖率什么都要做”。
> 新版按回归价值分档。**覆盖率不是目标**：按风险加权做到 60%~70% 即可，剩下靠手工 + 一次性探针。

### 判断标准

**值得深测（满足任意 2 条）**

1. **有写副作用或状态流转** —— 收藏→查状态→取消、提交记录→查列表→删除，手工最容易漏。
2. **鉴权 / 数据归属边界** —— 401、403、IDOR。成本最低、后果最重。
3. **确定性业务规则** —— BMI/BMR、日期区间、唯一性、分页边界，期望值能写死。
4. **历史上出过 bug 或高频改动** —— health 5 个接口曾挖出缺陷 #3~#8，必须长期守。

**不值得深测（或只做薄壳）**

1. **输出由模型 / 算法决定** —— 推荐排序、LLM 文案，硬断“必须推荐 A”只会造假红。
2. **纯透传 / 纯展示** —— 业务逻辑约等于 0。
3. **依赖不可控外部服务** —— 算法服务 5000 不在，接口失败不是被测系统的 bug。
4. **一次性运营操作** —— 手工点一次比写用例划算。

### 分档总览

| 档位 | 含义 | 接口数（约） | 建议投入 |
|---|---|:-:|---|
| **A 深测** | 业务 + 状态 + 越权 + 边界 | 30 | 每个接口 8~20 条 |
| **B 薄测** | 契约 + 分页/空值 + 权限 | 25 | 每个接口 2~4 条 |
| **C 冒烟** | 只断结构 / 降级 / 幂等 | 15 | 1~2 条或手工 |
| **D 不做** | 无独立逻辑 / 环境不可控 | 余下 | 手工 + 一次性探针 |

   **❌ 2026-10-28 实测更正：5 个管理接口、每种非法身份，全部是纯 403，一次 400 都没有。**
   原因：Spring Security 在**进业务层之前**就拦了，业务层那段 `requireAdmin()` 根本没机会执行。
   所以：
   - 断言可以直接写死 `== 403`，不需要 `in (403, 400)` —— 写宽了反而会让"某天 403 退化成 400"这种
     鉴权降级悄悄溜过去。
   - ~~403 的响应体是 Spring 默认错误体，不是统一信封（缺陷 #10）~~
     **❌ 2026-11-06 实测更正：缺陷 #10 已修复。** 403 现在返回
     `{"code":403,"message":"当前账号没有该操作权限，请使用管理员账号登录","data":null}`。
     所以 `assert_forbidden` 里"不能有 data 键"的判据已改成"data 必须为 null"
     （键存在但值是 null 是安全的，有内容才是泄露）。
   - ~~401 全站都是空响应体，不能 `resp.json()`~~
     **❌ 2026-11-06 实测更正：401 也统一成信封了**：
     `{"code":401,"message":"登录已过期，请重新登录","data":null}`（六个接口逐一验过）。
     旧用例里 10 处 `assert resp.text == ""` 因此假失败，已全部改为 `assert_error(...)`。
     ⚠️ 这类"后端改好了、断言还停在旧口径"的失败**不是回归**，
     是文档和用例需要跟着更新 —— 区分方法：看响应体是"更好了"还是"更差了"。

3. **`/recipe/*` 的认证声明与实际不符**（已实测）：文档写 `list` / `detail` / `search` / `nutrition` / `recommend` 是"无需认证"，但实测 **无 token → 401**。写用例时以**实测结果**为准，并记入缺陷单。

### ⚠️ 判定纪律：缺陷 = **与需求/设计不一致**，不是"与我的直觉不一致"

列进上表之前，先回答一个问题：**"应该这样"这句话，依据是什么？**
依据必须是下面之一，否则降级到「观察点」，别急着报 bug：

1. `API.md` / 前端页面 / 产品需求里**写明了的**；
2. 表结构、字段语义**明确表达的**（如 `update_time` 带 `ON UPDATE CURRENT_TIMESTAMP`）；
3. 团队**已经按某个标准修过同类问题**（先例）。

反面教材：我 2026-09-30 探测 `/user/profile` 时，把"传 `email` 不生效""`phone` 可以重复"直接写成了缺陷 #11/#12，
**却没回头核对需求** —— 前端编辑个人资料页根本没有邮箱输入框、`API.md` 只声明可改「用户名/手机号/头像」，
注册校验也只写了「用户名/邮箱查重」。两条都是**设计如此**，被我误判成 bug。

**这条纪律没被推翻，后续把完整流程走完了（同一天）**：

`phone` 重复先降级到观察点 **O2**（"设计如此"），用户确认"手机号必须唯一"之后——
它**从"设计如此"升级成"需求变更"**，于是按变更实现（缺陷 **#11**，已修复）。
所以正确姿势不是"别报"，而是**先确认、再定性**：

| 阶段 | 定性 | 该写在哪 |
|:--|:--|:--|
| 只看到"两个账号手机号相同" | 观察点（可能设计如此） | 观察点表（O2） |
| 确认"手机号要用于登录/找回密码，必须唯一" | **需求变更** | 缺陷表（并注明是变更） |
| 实现完成 + 回归通过 | 已修复 | 缺陷表 ✅ + 同步更新 `API.md` |

「`phone` 能重复」本身不是 bug；但确认后决定要做唯一，它就是一个变更 ——
**"观察到什么"和"决定改成什么"是两件事，在缺陷单上要分开写。**

> **查库验证写操作要加 `autocommit=True`**，或每次用新连接。

### 附带教训：缺陷修好了，用例却"假失败"——撞秒

`test_bug_update_time_not_refreshed` 断言的是 `after != before`，
而 `updateTime` 精度只到**秒**。文件级/全套连续跑时，**前一条用例的 teardown 还原**
和本用例的写入会落在同一秒，`after == before` → 断言失败 → 记成 XFAIL。
后端此时已经是好的，是**用例写法**制造了假失败。

**实测证据**：单独跑这条用例 6/6 通过（XPASS）；整个文件连着跑 4/4 失败（XFAIL）。

> 教训：断言"某字段变了"时，先看它的**时间精度**够不够分辨两次写操作；
> 不够的话，要么跨秒（`time.sleep(1.1)`），要么改判更有意义的东西——
> "这个时间戳是不是刷新成了刚才那一刻"。
> 完整改写代码见 `README.md` 第六节末尾。

| xfail 固化缺陷 | 12 条（#1~#12，其中 6 条已修复） | **20 条**（新增 8 条） |

**加的是 24 个接口，但只有 3 个模块做了深测。** 剩下的只做薄壳 —— 这个比例是故意的，
不是"时间不够先凑这么多"。理由下面逐条写。

### 二、必须覆盖的（A 档，三批共 43 条）

判断标准用的是 §三 那张表，三个模块各自命中了不同条款：

| 模块 | 条数 | 命中哪条标准 | 如果漏测会怎样 |
| --- | :-: | --- | --- |
| **食谱收藏四件套** | 14 | ①有写副作用+状态流转 ②数据归属边界 | 任何人能取消任何人的收藏；重复点收藏产生脏数据。**前端只看红心颜色，后端错了也看不出来** |
| **饮食记录 4 个接口** | 19 | ②数据归属边界 ③确定性业务规则 | `/record/detail/{id}` 只有 id 入参，拦不住就是全站记录可读；总热量算错则首页、趋势、AI 回答**全部跟着错且不报错** |
| **饮食偏好 GET/PUT** | 10 | ①有写副作用（影响推荐结果） | 全站唯一能改偏好的入口。改错了没有报错，只是推荐变得莫名其妙 |

这三批有一个共同点：**错了不报错**。这也是它们排在收藏/记录/偏好、
而不是排在本轮同样补了的食谱读接口前面的原因 —— 见下一条。

### 三、明确不做的（以及为什么"不做"是对的）

> §三 的原话是「覆盖率不是目标」。这一节就是把它落到实处：
> 下面每一个"不做"都有具体理由，不是"还没排上"。

| 接口 | 档位 | 为什么不做 | 替代做法 |
| --- | :-: | --- | --- |
| `/recommend/*` 4 个、`/recipe/recommend` | C | 排序由算法/模型决定，硬断"必须推荐 A"只会造假红；且依赖 Flask 5000，服务不在就整片红 | 只断 200 + 非空 + 字段形状；业务效果靠人工验收 |
| `/record/analysis/trend`、`/record/suggestions` | C | 同上，依赖算法服务 | 服务在时跑一条冒烟，不在就 skip |
| `/ingredient/nutrition`、`/ingredient/substitute`、`/recommend/ingredient/substitute` | C | LLM 依赖，输出不确定 | 只测降级分支（不提 key 的实例）或结构 |
| 食谱写类：`/recipe/save`、`update`、`delete` | B | **会写库且要清理**，而 `/recipe/update` / `/recipe/delete` 的归属校验已经由 `admin/test_admin_authz.py` 的鉴权矩阵覆盖了"能不能进"这一层。业务层（改一条食谱的字段正确性）价值低于它的清理成本 | 鉴权维度已有；业务维度等有真实运营需求时再补 |
| 食材管理端：`/ingredient/save` / `update` / `delete` | B | 同上。**这三个虽然是管理员接口，但路径不以 `/admin` 开头**，扫 `/admin` 扫不到，属于容易漏的盲区 → 已在 §三 A-① 的注里标出 | 鉴权矩阵按路径清单覆盖 |
| 文章写类 11 个：点赞 / 收藏 / 评论 / 发布 | B/C | **测试库 `health_article` 是空表（0 篇）**，没有靶子。硬写只能写"返回 200 就算过"，那种绿灯是负资产 —— 占着通过率，还让人以为测过了 | 先补文章靶子（下一轮），再补点赞/收藏闭环 |
| `POST /article/read/{articleId}`、`GET /article/read/history` | C | 埋点类，错了难发现、影响小 | 一条薄用例验幂等即可 |
| `/admin/overview`、`/article/admin/collect-stats` 的**业务正确性** | C | 看板数字，查库对账成本高 | 只测鉴权（已做） |
| `GET /recipe/list` 等读接口的**业务内容** | B | 就是 select，深测等于测 MySQL 会不会 select | 只断契约 + 鉴权 + 边界（本轮已做，5+4+5 个接口共 23 条） |
| `/assistant/chat` 降级分支（无 `DEEPSEEK_API_KEY`） | C | 8080/8081 上永远配着 key，当前环境触发不了 | 单独起不配 key 的实例后再补 |

**一句话概括这个取舍**：
> 一个接口值不值得写用例，看它「错了之后**会不会有人喊**」。
> 收藏错了、记录算错了、偏好被清了 —— 用户会喊，而且喊的时候你已经无法复现。
> 推荐排序不好、看板数字差 1 —— 没人喊，或者喊了也查不出。

### 四、这轮实测出的 8 条新缺陷

全部用 `xfail(strict=True)` 固化，修好那天会以 **XPASS** 形式跳出来提醒（不是静默变绿）。

| # | 一句话 | 类型 |
| --- | --- | --- |
| 13 | 收藏不存在的食谱 → 400 吐 MyBatis 外键异常（含库名/表名/约束名） | 安全·信息泄露 |
| 14 | 提交记录缺 `mealType` → 400 吐 SQL 异常原文 | 安全·信息泄露 |
| 15 | `mealType` 无枚举白名单，`"xxx"` 能入库 | 数据完整性 |
| 16 | `PUT /user/diet-preference` 响应体是请求回显，不是真实存储 | 契约不一致 |
| 17 | `/record/list` 的 `page`/`pageSize` 完全不生效 | 功能缺陷（会随时间恶化） |
| 18 | 明细负热量被接受，总量能算成 -500 | 数据完整性（影响核心价值） |
| 19 | `mealFrequency` 无范围校验，0/99 都能入库 | 数据完整性 |
| 20 | 三个 search 接口缺 `keyword` 都返回 Spring 默认错误体 | 契约不一致（#2 的完整版） |

**这批缺陷的共同点值得记下来**：13/14/20 都是「框架层或数据库层的错误漏到了用户面前」，
15/18/19 都是「数值/枚举没有范围校验」。前一类和已修复的 #3、#10、#12 同源，
后一类和已修复的 #4、#8 同源 —— **说明这两类问题在这个项目里是系统性的，不是偶发**。
所以它们用 xfail 钉住，而不是"报一次就完了"。

### 五、跑这批用例的两个环境前提（踩过的坑）

1. **后端必须连 `health_diet_test`，不是 `health_diet`。**
   本轮第一次跑就撞上了：后端连的是开发库（189 用户 / 253 食谱），
   测试框架连的是测试库（3 用户 / **0 食谱**），夹具插的食谱后端读不到 → 自检直接拦下。
   验证方法：`conftest.py` 的环境预检会用 `userId + username` 跟测试库对账，不一致就中止。
   本轮做法是**另起一个 8082 实例**（`DB_NAME=health_diet_test`），不动 8081，
   跑测试时用 `AUTOTEST_BASE_URL=http://127.0.0.1:8082/api` 指过去。

2. **测试库的 `recipe` / `health_article` 是空表。**
   `recipe` 由夹具现造（`test_cases/recipe/conftest.py` 的 `_insert_recipe`），
   `health_article` 没有造，所以文章写类全部留白 —— 这是上面「明确不做」表里的一行。

### 六、这轮顺手修的一个框架缺口

`common/cleanup.py` 的 `_USER_CHILD_DELETES` 原来只按 `user_id` 删收藏行。
收藏用例必然出现「B 收藏了 A 的食谱」，此时删 A 的账号要删 A 名下的 recipe，
而 B 那条收藏行还指向它 → **1451 外键约束失败**，teardown 直接报错。
已补两条「按 recipe_id 反查所有引用者」的删除（`user_recipe_collect` / `diet_record_detail`）。
> 教训：清理清单要按**"谁引用了我"**补，不能只按"我引用了谁"。
