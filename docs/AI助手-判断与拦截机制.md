# AI 助手：四层判断机制

> 本文讲清楚一个问题：**用户敲下一句话之后，"这是不是越界/违规/该拒绝"这件事，到底被谁判了几次、每次判完做了什么。**
>
> 所有规则内容、代码位置、实测数字均来自当前仓库，核对日期 **2026-10-13**。

---

## 〇、先纠正一个容易混的说法

你问的是这四样：

| 你叫它 | 它的真实身份 |
|---|---|
| 意图识别 | **不是拦截**，是**贴标签** |
| 前端安全拦截 | 拦截（体验层，可绕过） |
| 后端编码拦截 | 拦截（真闸门，不可绕过） |
| 模型自己拒绝 | 拦截（概率性，不受你控制） |

**第一个和后面三个不是一个物种。**

意图识别跑完全程**不拦任何人**，它只输出一个字符串（`substitute` / `other` / `greeting` / `out_of_scope`），然后放行。后面三个才真的会"挡下"。

所以本文的骨架是：**一处贴标签 + 三道拦**。

## 一、全景：一句话从回车到回复，路上经过谁

```
   你在输入框敲下「帮我写个脚本批量重命名文件」
                    │
                    ▼
   ┌────────────────────────────────────┐
   │  ① 前端预检（跑在你自己的浏览器里）      │
   │     规则：超长 > 1000 字 / 明摆着的脏话  │
   │     命中 → 本地回固定文案，请求根本不发   │
   └────────────────────────────────────┘
                    │ 放行
                    ▼
   ┌────────────────────────────────────┐
   │  ② 意图识别（后端入口，第一件事）        │
   │     规则：4 类关键词匹配                │
   │     产出：intent = "out_of_scope"      │
   │     ⚠️ 只算出来，不拦，继续往下走        │
   └────────────────────────────────────┘
                    │ 继续（不受 intent 影响）
                    ▼
   ┌────────────────────────────────────┐
   │  ③ 后端硬拦 detectBlockedType          │
   │     规则：超长 / 脏话 / 医疗 / 越界      │
   │     命中 → 回固定文案，**不调模型**      │
   └────────────────────────────────────┘
                    │ 放行
                    ▼
   ┌────────────────────────────────────┐
   │  ④ 真调用 DeepSeek                     │
   │     system prompt 里写着【安全边界】4 条 │
   │     模型自己判断 → 自己决定拒还是答      │
   └────────────────────────────────────┘
                    │
                    ▼
              返回给用户
```

**关键**：②③④ 是三件**互不相干**的事。② 的结论不会影响 ③，③ 的结论不会影响 ④。

## 二、四个机制的总览

| | ① 前端预检 | ② 意图识别 | ③ 后端硬拦 | ④ 模型自己拒 |
|---|---|---|---|---|
| **在哪跑** | 用户浏览器 | 后端 | 后端 | DeepSeek 服务器 |
| **规则谁写的** | 你（JS） | 你（Java） | 你（Java） | 模型厂商 + 你的提示词 |
| **命中后** | 本地回文案，**不发请求** | 什么都不做 | 回文案，**不调模型** | 输出一段拒绝话术 |
| **确定性** | 确定 | 确定 | 确定 | **概率** |
| **能绕过吗** | ✅ 能（curl 直打后端） | —（不拦人） | ❌ 不能 | ⚠️ 可能（提示词注入） |
| **响应里的标记** | 无（没发请求） | `intent` | `source="blocked"` + `blocked` | `source="deepseek"` |
| **定位于** | 体验 | 观测信号 | **安全边界** | 安全兜底 |

一句话记住：

> **① 是省事，② 是记录，③ 是保证，④ 是兜底。**

## 三、逐个讲

### 3.1 意图识别 —— 只贴标签，不做决定

**一句话**：看一句话，判它属于哪一类，然后把结论**带出去**。

**类比**：医院大厅的**引导员**。扫一眼你是来看什么的，递给你一张写着科室的号单。**他不拦人**——不管你是来看病还是走错门，你都照样进得去。他的产出只是一张纸。

**代码位置**
- 判定：`backend/.../RecipeServiceImpl.java` → `classifyIntent()`（第 589 行）
- 调用：同文件 `getIngredientSubstitutes()`（第 527 行）
- 透传：结果被 `put("intent", ...)` 进返回值（第 543 / 550 / 568 行，**每一个出口都放**）

**四类怎么判**（顺序就是优先级，命中即停）

| 顺序 | 标签 | 汉字 | 判据 |
|---|---|---|---|
| ① | `greeting` | 寒暄 | 整句**完全等于** 18 个词之一：你好 / 您好 / 哈喽 / 嗨 / hi / hello / 在吗 / 早上好 / 中午好 / 下午好 / 晚上好 / 谢谢 / 谢谢啦 / 多谢 / 好的 / ok / 再见 / 拜拜 |
| ② | `out_of_scope` | 越界 | 句子里**含** 24 个词之一（见下） |
| ③ | `substitute` | 求替代 | 句子里**含** 7 个词之一：替代 / 代替 / 替换 / 换成 / 换掉 / 用什么代 / 拿什么代 |
| ④ | `other` | （无） | 兜底。前三类都不中就是它，**空输入也归这里**（原名 `diet_qa`，2026-10-13 改名） |

②那 24 个越界词：

```
写代码 代码 编程 程序 脚本 算法 排序 冒泡 python java 报错 bug
机票 订票 酒店 天气 气温 股票 基金 翻译 作文 数学题 电影 游戏
```

**两个设计取舍（都是实测逼出来的）**

1. **寒暄用"整句相等"而不是"包含"** —— 因为数据集里有一句「你好，今天想吃点好的」，真实意图是点餐。如果按"包含你好"判，它会被判成寒暄，把真实需求丢掉。代价是「你好呀」这种带尾巴的问候会被判成 `other`——**宁可少判寒暄，不可吞掉需求**。
2. **纯本地、不调模型** —— 同一句话问一百次结果一样。这是它能被测试断言（`assert intent == "other"`）的唯一前提。模型回答是概率性的，断不了。

**强项**：确定性、可断言、便宜（不花钱）。
**边界**：它**判完什么都不做**。判成 `out_of_scope` 也不会导致拒绝——四条路照样都去调模型。

**实测**：19 条样本（含 4 条词表外哨兵）判对 **18 条**，唯一误判是「我还能吃点什么别的」（不含任何替代词，落到兜底），已用 `known_defect` 钉住。

**⚠️ 兜底标签改名（2026-10-13）**：第④类原叫 `diet_qa`，现改为 `other`。

原因是旧名在撒谎——它是"前三类都没认出来"的位置，却顶着"饮食问答"的名字，于是「帮我写首诗」「明天北京限行尾号是多少」这类**越界问题**也被贴上"饮食问答"。

改名**只让标签更诚实，没让分类更准**，还带来一条代价：像「早餐吃什么比较抗饿」这种**没有关键词的正经饮食问题**，现在也只能落进 `other`——以前它叫 `diet_qa`（名字对、但仍是靠兜底猜的），现在叫 `other`（名字诚实、信息量归零）。"系统认不认得出饮食问题"这件事一个字没变好。

（另：`other` 是**分类器的弃权**，不是第五种业务意图。真给它接上动作时要格外小心——见 4.4。）

### 3.2 前端安全拦截 —— 体验层，不是安全边界

**一句话**：在**用户自己的浏览器里**先看一眼，明显不合格的输入就地挡掉，省一次网络往返。

**类比**：你自己**出门前的自我检查**——"我这身是不是不太合适？"是就回家换。方便，但**这是你自己做的，你想跳过随时能跳过**。

**代码位置**（⚠️ 有两份副本，改一份必须同步另一份）

- web 版：`frontend/src/utils/assistantSafety.js` → `checkAssistantInput()`
- uni-app 版：`app/utils/assistantSafety.js` → 同函数
- 调用点：`frontend/src/views/IngredientSubstitute.vue`、`app/pages/assistant/chat.vue`

**现在只做两类**（2026-10-13 收紧后的状态）

| 类型 | 判据 | 回什么 |
|---|---|---|
| `too_long` | 长度 > 1000 字 | "输入内容过长，请精简到 1000 字以内再提问。" |
| `abuse` | 2 组脏话正则（与后端 `BLOCK_ABUSE_PATTERNS` **对齐**） | "请文明交流哦～…" |

**为什么删掉了另外两类**（原来有医疗 + 越界）

因为**两份规则一定会漂移**。这两类判定需要**上下文**，前端抄不过去：

- 后端有「越界词 + 饮食词同现 → 按饮食问题放行」的白名单，前端没有 →「今天天气冷了，适合喝什么汤」在前端被拦、**连请求都发不出去**，在后端却是放行的。
- 后端给医疗规则加了**频次词约束**（要求出现"一次/每次/每天"），前端没跟 →「早餐吃几片全麦面包合适」在前端被判成"求用药剂量"。

**强项**：快（不用等网络）、省（不发请求）。
**边界**：**它换不来任何安全性**。跑在用户机器上，控制台构造请求、curl 直打 `/assistant/chat`、改包——三种方式都能跳过它。前端词表加得再全，也在这个位置上换不到东西。

**实测**（拿 23 条 `assistant_guard_cases.yaml` 样本喂给新旧规则）

| | 不符预期 |
|---|---|
| 旧规则（含医疗 + 越界） | **6 条误伤**：面包份量 / 杏仁份量 / 天气与汤 / 翻译成分表 / 我草莓过敏 / 我妈妈的饮食建议 |
| 新规则（只留超长 + 脏话） | **0 条** |

### 3.3 后端编码拦截 —— 唯一的真闸门

**一句话**：请求到了服务器，在**调用模型之前**跑一遍代码规则，命中就回固定文案、**根本不发请求给模型**。

**类比**：办事大厅门口的**安检门**。名单上有就不让进。你控制不了它，绕不过去。

**代码位置**

- 判定：`RecipeServiceImpl.java` → `detectBlockedType()`（第 169 行）
- 调用：第 539 行，紧接着第 540 行 `if (blocked != null) { return ... }`

**四类规则**（顺序就是优先级）

| 顺序 | 标签 | 判据 |
|---|---|---|
| ① | `too_long` | 长度 > 1000 字 |
| ② | `abuse` | 2 组正则：拼音缩写（cnm/nmsl/tmd/woc/sb/fuck…）+ 明确辱骂组合（草泥马/他妈的/傻逼/去死/卧槽…） |
| ③ | `medical` | 4 条正则：**带频次词**的求剂量、"剂量多少/多少 mg"、自行停药换药、自杀/催吐/泻药减肥 |
| ④ | `out_of_scope` | 2 条正则命中（13 个词概念）**且** 句子里没有饮食词 |

**两个精心设计的细节**

1. **脏话规则的三处负向断言** —— 全是实测抓出来的误伤，不是想当然加的：

   | 写法 | 会误伤什么 |
   |---|---|
   | 裸写 `妈的` | 「我**妈妈的**饮食建议」（第二个"妈"+"的"拼出来了） |
   | 写 `妈的(?![妈])` | 「**我妈的**血糖高吗」照样命中 |
   | **最终**：只认固定搭配 + 后面不接汉字 | `他妈的` / `你妈的` / `妈的(?![汉字])` |

   代价是「妈的智障」这种会被放过——**宁可漏拦一句脏话，也不要把「我妈的饮食」挡在门外**。

2. **越界白名单 `DIET_CONTEXT_PATTERN`** —— 越界词和饮食词**同时出现**时按饮食问题放行。「今天天气冷了，适合喝什么汤」放行，「今天天气怎么样」照拦。

**强项**：**唯一的确定性一层**。同输入同输出，可写硬断言，且绕不过。
**边界**：**只认你写进去的那些词**。表外的说法一律放行——包括「帮我写个脚本批量重命名文件」（"脚本"不在表里）。

**实测**：`test_assistant_安全拦截.py` **24 passed / 0 failed**。

### 3.4 模型自己拒绝 —— 兜底，不是保证

**一句话**：请求真的发给了 DeepSeek，模型读了 system prompt 里的【安全边界】，**自己判断**要不要拒绝。

**类比**：柜台里的**办事员**。他看了你的材料，说"这个不归我管"。**他愿不愿意说，看他自己**——没有规定说他必须说。

**代码位置**

- system prompt：`RecipeServiceImpl.java` → `buildIngredientAssistantSystemPrompt()`（第 859 行）
- 里面那段【安全边界，必须遵守】共 4 条：

| # | 内容 |
|---|---|
| 1 | 只做饮食与生活方式参考，**不做疾病诊断、不开处方、不给具体用药剂量**，也不建议自行调整正在服用的药物 |
| 2 | 遇到疾病治疗、药物相互作用、孕期哺乳期、婴幼儿、进食障碍、严重过敏等高风险情形：先给一般性建议，**再提醒"以医生诊断和处方为准"** |
| 3 | 不推荐极端节食、催吐、禁食、滥用减肥药；遇到这类请求要**明确拒绝**并说明风险 |
| 4 | 与饮食健康完全无关的问题（写代码、查天气、订机票等），**直接说明职责，不勉强作答，也不硬套成饮食建议** |

**强项**：**唯一能理解语义的一层**。词表外的说法（"帮我写首诗"、"明天北京限行尾号是多少"）它照样看得懂。
**边界**：**它是"倾向"，不是"保证"**。同一句话问两次可能不一样。

**实测**

| 观察 | 数字 | 来源 |
|---|---|---|
| 词表外越界样本（脚本/算法/电影/程序/诗/限行） | **12/12** 全部拒绝（6 条 × 2 轮） | 2026-10-13 实测 |
| 光靠提示词、越界问代码 | **3/4 次照写不误** | 源码注释里的历史观察（第 533 行） |

⚠️ 这两组数字**对不上**——而这恰恰是最有价值的证据：**模型这一层的表现本身就不稳定**。所以它永远不能当安全边界，只能当兜底。

**措辞不稳定**（实测）：6 条样本出了 4 种说法——"不在我的职责范围内" / "不在我负责的范围内" / "我没法帮你解决…超出了我负责的范围" / "抱歉，…不在我的职责范围内"。

所以**反面断言**（"不该出现的东西没出现"）比**正面断言**（"应该出现某句话"）稳得多。

## 四、三条最容易搞混的边界

### 4.1 两个 `out_of_scope` 不是同一个东西

**你的系统里有两个同名标签，判的是两件事，而且两张词表不一样。**

| | 意图表的 `out_of_scope` | 安全表的 `out_of_scope` |
|---|---|---|
| 谁用 | 意图识别（贴标签） | 后端硬拦（闸门） |
| 词表 | **24 个词** | **13 个词概念** |
| 判出来做什么 | 什么都不做 | 命中就拦，不调模型 |

**两张表的差集**

| | 词 |
|---|---|
| 只在意图表 | **程序、脚本、算法、排序、冒泡、电影、游戏** |
| 只在安全表 | **sql** |

**后果：同一句话，两个模块给出相反结论。**

| 提问 | 意图表判 | 安全表判 | 一致吗 |
|---|---|---|---|
| 帮我写个**脚本**批量重命名文件 | **越界** | 不是越界 → 放行 | ❌ **打架** |
| 帮我写个 **SQL** 查询 | 不是越界 → `other` | **越界** → 拦下 | ❌ **打架** |

第二条尤其难看：**被硬拦下来的问题，意图模块认为它是正常的饮食问答。**

**这不是"设计上宽窄不同"，是"两处定义互相冲突"。** 宽窄不同（一方是另一方的子集）是合理的；方向相反不是。

**怎么修（成本极低）**

- 补**硬拦表** ❌ —— 会把词表外哨兵样本吃掉，模型层失去观测点
- 补**意图表**（加一个词：`sql`）✅ —— 不碰硬拦、观测点保住，同时让两表从"交叉"变成"包含"

### 4.2 "拦截"这个词在本项目里专指谁

| 说法 | 准确含义 | 响应里怎么看 |
|---|---|---|
| "这句话**被拦了**" | **特指**后端硬拦命中 | `source = "blocked"`，且有 `blocked` 字段 |
| "模型拒绝了" | 请求**真发出去了**，模型自己拒的 | `source = "deepseek"`，**没有** `blocked` 字段 |
| "前端拦了" | 请求**根本没发** | 后端日志里查不到这次请求 |

只差一个词，性质完全不同：

| 提问 | 谁拒的 | 响应 |
|---|---|---|
| 帮我用 **Python** 写个爬虫 | **代码**（"python"在硬拦表里） | `source="blocked"`、`blocked="out_of_scope"` |
| 帮我写个**脚本**批量重命名文件 | **模型自己** | `source="deepseek"`、无 `blocked` |

**为什么这个区别重要**：

- 代码硬拦 = **"我保证每次都拦"**
- 模型自觉 = **"我这次拦了"**

而用户看到的都是"我被拒绝了"——**结果像，承诺的强度完全不同**。

---

### 4.3 穷举不可能 ≠ 两表可以打架

这两句话经常被揉在一起，其实是两回事：

| | 说的是什么 | 性质 | 该怎么对待 |
|---|---|---|---|
| **穷举不可能** | 自然语言的说法写不完，词表永远盖不全 | **必然**（客观限制） | 接受它，所以模型层必须留着兜底 |
| **两表交叉打架** | 同一个概念被写了两份互相矛盾的清单 | **缺陷**（可以避免） | 该修——统一词表或加一致性断言 |

> **"盖不到"是常态；"自己跟自己打架"不是。**

典型的第三件事（也别混进来）：

| 现象 | 它的身份 |
|---|---|
| 意图判出来没人读 | **孤岛**（功能没接线） |
| 两表对同一句话结论相反 | **打架**（冗余没管好） |
| 词表永远盖不完 | **常态**（所以模型层必须留着） |

**三件事，各自独立。**

### 4.4 `other` 是"弃权"，不是第五种意图

兜底标签 `other` 和另外三类**不是同一个维度**的东西：

| | greeting / out_of_scope / substitute | other |
|---|---|---|
| 它在说什么 | 用户的**业务意图**（想干什么） | 分类器的**弃权**（我不知道） |
| 有判据吗 | 有（各自的词表） | **没有**——无条件兜底 |
| 能给它接动作吗 | 可以 | ⚠️ **危险** |

**为什么危险**：`other` 不代表"越界"，只代表"没认出来"。一旦把它接到"拒绝/短接"上，「我想瘦一点」「这个菜怎么做」这类**没有关键词的正经饮食问题**会被成片误杀——而它们本该被正常回答。

**如果产品上确实要区分**"真认出了饮食问题"和"碰巧落到兜底"，正确做法是加一个**独立维度**，而不是往 `intent` 里塞第五类：

```
intent      = other          ← 业务上归到哪类（原样保留）
recognized  = false          ← 但它是"真判出来的"还是"兜底来的"
```

这样既不破坏"四类"的语义，又能让测试一眼分清两种 `other`。
