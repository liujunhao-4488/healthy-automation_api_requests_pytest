## 一、系统是什么

健康饮食智能管理系统是一套面向普通用户的全栈健康饮食管理平台。它围绕**"建档 → 定目标 → 记饮食 → 智能推荐 → 学知识 → 答疑"**形成完整闭环：

- 用户先填写健康档案（年龄、身高、体重、活动量、慢病等），系统自动算出 BMI 与 BMR；
- 再设定饮食目标（减肥 / 增肌 / 控糖 / 维持健康）与每日热量、三大营养素配比；
- 每天记录三餐与加餐，系统汇总热量与蛋白质 / 碳水 / 脂肪，对比目标给出趋势和调整建议；
- 推荐引擎结合档案、目标与偏好，给出三餐食谱候选；还能对单一样食材给出营养等价的替代方案；
- 遇到"高血脂怎么吃"这类问题，可在 AI 助手里获得基于权威食养指南（RAG）的有据可依回答。

系统覆盖 **Web 端、移动端、后台管理**三端，并配套完整的 **接口自动化测试体系（346 条用例）与 CI 流水线**，是一套"能跑起来、能测起来、能进流水线"的完整工程。

## 二、解决什么问题

| 用户痛点 | 系统对应的能力 |
| --- | --- |
| 知道要减肥 / 控糖，但不知道每天具体吃什么 | 根据档案 + 目标自动生成早 / 午 / 晚餐推荐 |
| 记了几天饮食就断了，看不到效果 | 饮食记录 + 摄入趋势分析 + 目标达成建议 |
| 忌口、过敏、不喜欢某种食材 | 饮食偏好（过敏原 / 忌口 / 喜好）参与推荐过滤，支持食材替代 |
| 网上养生信息真假难辨、AI 回答不靠谱 | RAG 检索权威食养指南 + 站内文章，回答带来源与引用 |
| AI 越界做医疗诊断、被诱导越狱 | 后端硬拦截：辱骂 / 医疗诊断 / 超长输入 / 提示词注入 |

> 系统定位为**饮食与营养建议工具**，不提供医疗诊断、不开处方、不替代医嘱；在线支付、电商交易、在线问诊不属于本期范围。

│  鉴权 / 业务 / 数据组装   │        │  health_diet         │

             │  推荐 / RAG 检索      └─────────────────────┘

┌──────────────────────────┐        ┌─────────────────────┐
│  算法服务 Flask :5000     │───────▶│  权威文件 / 站内文章  │

             ▲
             │  接口自动化（346 条，pytest + Allure）
┌────────────┴─────────────┐

└──────────────────────────┘

### 3.1 分层说明

| 层 | 技术栈 | 职责 |
| --- | --- | --- |
| 表现层 | Vue 3 + Vite + Element Plus + ECharts + Pinia；uni-app 移动端 | 档案引导、记录录入、图表趋势、AI 聊天（SSE 流式）、后台管理 |
| 业务层 | Spring Boot 2.7 / Java 21 + MyBatis-Plus + Spring Security(JWT) | 统一响应信封、鉴权与角色控制、业务规则、调用算法服务、调用大模型 |
| 算法层 | Python Flask | 食谱推荐引擎（V1 规则 / V2 混合）、RAG 知识库检索与索引运维 |
| 数据层 | MySQL 8.0（utf8mb4，19 张表） | 用户、档案、目标、记录、食谱、食材、文章、会话、通知等 |

### 3.2 关键设计取舍

- **业务与算法分离**：推荐与检索放在独立 Flask 服务，后端只做业务编排，算法可单独迭代、单独评测。
- **推荐可降级**：V2 混合引擎需通过"结构合法 → 每餐覆盖率 ≥ 60% → 平均匹配分 ≥ 阈值"三层校验，任一不达标或异常即回退 V1 纯规则引擎，保证始终有结果。
- **失败隔离**：算法服务异常、检索为空、大模型不可用都不会导致后端 500 白屏，而是降级返回空数据或可读提示。
- **安全以后端为准**：前端规则可被 curl 绕过，因此所有拦截（AI 安全、角色越权、参数校验）都在后端代码层实现。

### 4.1 智能推荐怎么做

1. **输入**：健康档案（年龄、BMI、活动量、慢病、过敏）+ 饮食目标（热量、配比）+ 饮食偏好 + 候选食谱集。
2. **V2 混合引擎**：SVD 协同过滤捕捉"相似用户喜欢什么" + GBDT 营养匹配打分衡量"这餐是否符合我的目标" + 规则护栏处理过敏、忌口、慢病禁忌。
3. **质量闸门**：结构合法、每餐覆盖率 ≥ 60%、平均匹配分 ≥ 阈值（默认 55），不达标自动回退。
4. **V1 规则引擎**：纯规则打分兜底，保证任何情况下都有推荐结果。
5. **可调**：`RECOMMEND_ENGINE_MODE=auto/v2/legacy`、`RECOMMEND_V2_MIN_MATCH_SCORE` 可在线调整策略与门槛。

### 4.2 AI 助手怎么做

- **意图路由**：先判定 `knowledge`（知识问答，再分"食材精确查表"与"文章 RAG 检索"）、`advice`（饮食建议，携带本人健康画像）、`recipe`（食谱推荐）、`chat`（通用问答）。
- **RAG 双源**：权威源为卫健委各类人群 / 慢病食养指南 PDF，切片入库；站内源为健康文章。有唯一数值答案的问题（如"米饭多少卡"）走精确查表，不进检索，避免大模型编数字。
- **检索容错**：连接 / 读取超时 1.5s / 3s，检索超时不影响聊天主链路。
- **可观测**：每条回复带 `intent`、`source`、`blocked` 标记，便于评测与问题定位。
- **安全护栏**：辱骂（abuse）、越界医疗（medical）、超长输入（too_long）命中即返回固定拒答；同时防御提示词注入与越狱。

## 五、数据模型概览

数据库 `health_diet`（测试库 `health_diet_test`）共 **19 张表**，核心实体：

```
user ──┬── health_info ── health_info_history
       ├── diet_goal
       ├── diet_record ── diet_record_detail ── ingredient
       ├── user_diet_preference
       ├── user_recipe_collect / user_article_collect / user_article_like / user_read_record
       ├── assistant_conversation ── assistant_message
       └── notification

ingredient ── recipe_ingredient ── recipe
health_article ── article_comment
```

**数据规则**：记录、评论、通知、会话以软删除为主；外键用 `RESTRICT` 防止误删被引用数据；时间统一 `yyyy-MM-dd HH:mm:ss`；开发库与测试库物理隔离，测试脚本禁止清空开发库。

## 七、典型使用流程

1. **注册登录** → 首次进入走"基础信息 → 详细信息"两步建档，系统算出 BMI / BMR。
2. **设定目标**：选择减肥 / 增肌 / 控糖 / 维持，设置每日热量、三大营养素配比与饮水目标。
3. **查看今日推荐**：系统按档案、目标与偏好推送早 / 午 / 晚餐，可查看食谱详情与营养分析。
4. **记录饮食**：录入三餐与加餐，系统汇总当餐营养，与目标对比。
5. **看趋势与建议**：查看热量 / 营养素趋势，获得针对性的饮食调整建议。
6. **换着吃**：对某样食材调用替代，获得营养等价的替换方案。
7. **随时问**：在 AI 助手中提问，获得带权威指南出处的回答。
8. **日常维持**：浏览健康文章、接收通知提醒，管理员在后台维护内容与数据。

## 八、边界与后续演进

**明确不做**：在线支付、电商交易、医疗器械对接、医生在线诊疗与处方开具。

**后续待明确**（详见需求文档第 8 节）：慢病专项推荐策略与免责话术、饮水 / 运动 / 体重打卡是否纳入、文章个性化排序、短信与 App 推送通道、营养师与内容审核角色、运营指标口径。
