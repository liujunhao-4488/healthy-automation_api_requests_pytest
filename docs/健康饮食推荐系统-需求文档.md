## 1. 文档概述

### 1.1 编写目的
明确"基于 AI 的个人健康饮食推荐系统"的建设目标、用户角色、功能边界、业务规则、数据结构、非功能要求与验收口径，作为开发、联调、测试和后续迭代的统一依据。

### 1.2 项目背景
面向有体重管理、营养均衡、慢病饮食调理需求的普通用户，提供一套从"建立健康档案 → 设定饮食目标 → 记录每日饮食 → AI 智能推荐食谱 / 食材替代 → 学习健康知识 → AI 助手答疑"的闭环工具。系统在规则推荐基础上引入机器学习推荐与基于权威食养指南的 RAG 问答，提升推荐个性化程度与回答可信度。

### 1.3 项目范围
- **包含**：用户账号与权限、健康档案、饮食目标、饮食记录、智能食谱推荐、食材替代、食谱库、食材库、健康文章社区、AI 助手问答、通知中心、后台管理总览、Web 端与移动端。
- **不包含**（本期边界）：在线支付、电商交易、医疗器械对接、医生在线诊疗、处方开具；系统仅提供饮食与营养建议，**不替代医疗诊断与医嘱**。

### 1.4 术语与缩写
| 术语 | 含义 |
| --- | --- |
| BMI | 身体质量指数 = 体重(kg) / 身高(m)² |
| BMR | 基础代谢率，静息状态下每日所需热量 |
| RAG | 检索增强生成，先从权威知识库检索片段，再交由大模型组织回答 |
| CF | 协同过滤（Collaborative Filtering），本项目使用 SVD 嵌入 + 余弦相似度 |
| GBDT | 梯度提升决策树，用于营养匹配打分 |
| SSE | Server-Sent Events，服务端流式推送，用于 AI 逐字输出 |
| JWT | JSON Web Token，登录鉴权凭证 |
| 宏量营养素 | 蛋白质、碳水化合物、脂肪（供能三大营养素） |

## 2. 总体描述

### 2.1 产品定位
一款"个人健康饮食管理 + AI 个性化推荐"的轻应用，帮助用户把抽象的健康目标（减肥 / 增肌 / 控糖 / 维持健康）落到"今天三餐吃什么、用什么替代、每天摄入是否达标"的可执行层面。

### 2.2 用户角色
| 角色 | 说明 | 主要权限 |
| --- | --- | --- |
| 普通用户（user） | 注册使用的个人用户 | 管理本人档案 / 目标 / 记录 / 收藏 / 会话；浏览公开食谱、食材、文章 |
| 管理员（admin） | 平台运营人员 | 普通用户全部能力 + 用户管理、食材 / 食谱 / 文章 / 通知的后台维护、总览统计 |
| 游客（未登录） | 未注册或未登录访问者 | 可浏览公开食谱列表 / 详情 / 搜索、食材列表 / 详情 / 搜索、文章列表 / 详情 / 搜索；推荐、记录、收藏、评论、AI 助手需登录 |

### 2.3 典型使用场景
1. 新用户注册 → 填写基础健康信息（年龄、性别、身高、体重、活动量、慢病）→ 设定减肥目标与每日热量 / 宏量营养素配比 → 获得三餐推荐。
2. 用户记录早餐 / 午餐 / 晚餐 / 加餐，系统汇总当日热量与三大营养素，对比目标给出趋势与建议。
3. 用户想把鸡胸肉换成低脂食材，调用食材替代获得等价替换方案。
4. 用户在 AI 助手中提问"高血脂人群饮食要注意什么"，系统检索权威食养指南后给出有据可依的回答。
5. 管理员在后台查看平台用户 / 内容汇总、热门食谱与文章、发布系统通知。

## 3. 功能需求

> 统一响应信封：`{ "code": 200, "message": "操作成功", "data": {} }`；健康分析类接口额外返回 `analysis` 字段。前端以业务 `code==200` 判断成功，不能只看 HTTP 200。

### 3.1 账号与认证（FR-AUTH）
| 编号 | 功能 | 规则与要求 |
| --- | --- | --- |
| FR-AUTH-01 | 注册 | `POST /auth/register`，提交用户名、邮箱、密码、手机号；用户名 / 邮箱唯一，重复返回"用户名已存在 / 邮箱已被注册"；密码长度 6–50；邮箱格式校验；注册成功直接签发 JWT 并返回用户信息 |
| FR-AUTH-02 | 登录 | `POST /auth/login`，邮箱 + 密码；失败区分"用户不存在 / 密码错误 / 账号已被禁用"；成功返回 `token`、`userId`、`username`、`email`、`role` |
| FR-AUTH-03 | 鉴权 | 除公开接口外，请求头携带 `Authorization: Bearer <token>`；Token 缺失 / 无效 / 过期返回 401；前端路由守卫在 Token 过期时清除本地登录态并跳转登录 |
| FR-AUTH-04 | 角色控制 | `role=admin` 可访问后台管理接口，普通用户访问管理接口返回 403 / 业务 400 |
| FR-AUTH-05 | 账号状态 | 用户 `status`：1 正常、0 禁用；禁用用户不可登录、不可接收定向通知 |

### 3.6 智能食谱推荐（FR-RECO）
| 编号 | 功能 | 规则 |
| --- | --- | --- |
| FR-RECO-01 | 三餐推荐 | `GET /recommend/recipes?breakfastCount=&lunchCount=&dinnerCount=`，分别返回早餐 / 午餐 / 晚餐候选列表，数量可指定（默认各 3） |
| FR-RECO-02 | 今日推荐 | `GET /recommend/recipes/today` 返回当日推荐 |
| FR-RECO-03 | 推荐输入 | 用户健康档案（年龄 / BMI / 活动量 / 慢病 / 过敏）、饮食目标（热量 / 配比）、候选食谱集；结合饮食偏好（过敏原、忌口、喜好）过滤 |
| FR-RECO-04 | 引擎与降级 | auto 模式优先 V2 混合引擎（SVD 协同过滤 + GBDT 营养匹配 + 规则护栏）；结果须通过"结构合法 → 每餐覆盖率 ≥ 60% → 平均匹配分 ≥ 阈值（默认 55）"三层校验，任一不达标或 V2 异常，自动回退 V1 纯规则引擎，保证始终有结果返回 |
| FR-RECO-05 | 引擎可切换 | 环境变量 `RECOMMEND_ENGINE_MODE=auto/v2/legacy`，`RECOMMEND_V2_MIN_MATCH_SCORE` 调节质量阈值 |

### 3.11 AI 助手（FR-ASSISTANT）
| 编号 | 功能 | 规则 |
| --- | --- | --- |
| FR-AI-01 | 会话管理 | 会话列表、创建会话、查看会话消息、删除会话；会话含标题（取首条用户消息前若干字）、摘要、消息数、最后活跃时间 |
| FR-AI-02 | 问答 | `POST /assistant/chat`，入参 `conversationId`、`rawPrompt`（原始问题）、`prompt`（携带上下文后的问题）；返回会话、用户消息、助手消息 |
| FR-AI-03 | 流式输出 | 支持 SSE 逐字推送（`chatStream`），在独立线程发送事件，保证先返回 Emitter 再异步生成 |
| FR-AI-04 | 意图识别与路由 | 后端 `classifyIntent` 先判定意图：`knowledge`（营养数值 / 慢病 / 饮食概念，二级路由 `ingredient` 精确查表 或 `article` 走 RAG 检索）、`advice`（怎么吃 / 减肥 / 增肌 / 食谱搭配，携带本人健康档案画像）、`recipe`（食谱推荐）、`chat`（通用问答）；回复带 `intent`、`source`、`blocked` 标记 |
| FR-AI-05 | 大模型与 RAG | 问答由后端调用可配置大模型（现状 DeepSeek，`deepseek-chat`，base-url / api-key / model 走配置）；RAG 双源检索：权威源 `authority`（卫健委各类人群 / 慢病食养指南 PDF，切片入库）+ 站内文章 `article`；`/api/kb/search` 支持 `sourceType=authority/article/all`、`topK`（默认 3）；有唯一数值答案的（如"米饭多少卡"）走精确查表，不进检索；检索连接 / 读取超时 1.5s / 3s，超时不拖垮聊天 |
| FR-AI-06 | 两种回复形态 | 纯文本 `text` 或结构化卡片 `cards`（如推荐食材 / 食谱卡片），消息按 `messageType` 区分 |
| FR-AI-07 | 安全护栏 | 后端代码层硬拦截（前端规则可被 curl 绕过，故以后端为准）：`abuse` 辱骂 / 脏话、`medical` 越界医疗诊断 / 开处方、`too_long` 输入超 1000 字，命中时 `blocked` 标记并返回固定拒答；同时防御提示词注入、越狱（jailbreak）；通用生活问题不强行追问健康档案 |
| FR-AI-08 | 知识库运维 | `/api/kb/reload` 免重启重建索引；`/api/kb/stats` 查看权威 / 文章切块数、去重数；更换语料后需重跑入库脚本并重启 / 重建 |

## 4. 数据需求（核心数据表）

共 19 张表，主要实体如下（库 `health_diet`，utf8mb4）：

| 表 | 作用 | 关键关系 |
| --- | --- | --- |
| `user` | 用户，role=user/admin，status 1/0 | 用户名、邮箱、手机唯一 |
| `health_info` | 当前健康档案 | 1 用户 1 档案 |
| `health_info_history` | 体重 / BMI / 运动历史 | 关联 user |
| `diet_goal` | 饮食目标 | 关联 user |
| `diet_record` / `diet_record_detail` | 餐次主记录 / 食材明细 | 主从一对多，明细可关联食材、来源食谱 |
| `ingredient` | 食材营养库 | 分类、每 100g 营养、GI、钠、胆固醇 |
| `recipe` / `recipe_ingredient` | 食谱 / 食谱用料 | 主从，用料关联食材 |
| `health_article` | 健康文章 | 分类、标签、互动计数、状态 |
| `article_comment` | 评论（支持楼层 / 回复） | parent_id、reply_to_user_id |
| `assistant_conversation` / `assistant_message` | AI 会话 / 消息 | 主从，消息含 role、cards_json、message_type |
| `notification` | 通知 | 关联 user，类型 / 已读 / 软删 |
| `user_diet_preference` | 饮食偏好 / 过敏 / 忌口 | 关联 user |
| `user_recipe_collect` / `user_article_collect` | 食谱 / 文章收藏 | (user, target) 唯一 |
| `user_article_like` | 文章点赞 | (user, article) 唯一 |
| `user_read_record` | 阅读行为 | 时长 / 是否读完 / 滚动百分比 |

**数据规则**：删除类（记录、评论、通知、会话）以软删除（`is_deleted`）为主；外键以 `RESTRICT` 约束保护，避免误删被引用数据；金额 / 营养数值使用 double，时间统一 `yyyy-MM-dd HH:mm:ss`，日期 `yyyy-MM-dd`。

## 5. 接口与集成需求

1. **Web → 后端**：Vite 代理 `/api/*`，统一 JSON、JWT 头。
2. **后端 → 算法服务(Flask:5000)**：食谱推荐 `POST /api/recommend/recipes`、知识库检索 `POST /api/kb/search`（另含 `/api/kb/reload`、`/api/kb/stats` 运维接口）；后端配置算法服务地址。
3. **后端 → 大模型**：AI 问答由后端直接调用 DeepSeek（`deepseek-chat`），RAG 检索片段由算法服务提供后拼入 prompt；食材替代 / 营养数值由后端查库或结合模型流式生成。
4. **算法服务内部分层**：推荐引擎 V1（规则，兜底）/ V2（ML，优先）；RAG 检索器独立，权威指南与站内文章双源，支持分源召回评测。
5. **失败隔离**：算法服务异常、检索为空、V2 质量不足均不得导致后端 500 白屏，须回退或返回可读错误 + 空数据，并区分"检索成功未命中"与"服务故障"。
6. 接口明细见仓库 `API.md`（认证、用户、健康、目标、记录、推荐、食谱、食材、文章、AI 助手、通知、后台）。

## 9. 附录：本地启动基线

1. MySQL 启动，导入 `database/health_diet.sql`（开发库）；自动化用 `database/rebuild_test_db.bat` 建测试库。
2. 算法服务：`cd algorithm && pip install -r requirements.txt && python app.py`（:5000）。
3. 后端：`cd backend && mvn clean package -DskipTests && java -jar target/health-diet-backend-1.0-SNAPSHOT.jar`（:8080）。
4. Web：`cd frontend && npm install && npm run dev`（:5173）。
5. 移动端：`cd app` 后按 uni-app 流程运行，真机使用局域网 IP。
